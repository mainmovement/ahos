Section 2: Complete System Architecture
2.1 Architectural Model Overview
AHOS implements a four-tier, event-driven architecture with governance enforced as a cross-cutting concern across all operational tiers. The architecture is designed around clear separation of concerns, deterministic data flow, and fail-closed safety principles.

Tier Model:

text

TIER 0: FOUNDATION
├─ Event Bus (durable message backbone with guaranteed delivery)
├─ Database Layer (single source of truth, ACID guarantees)
├─ Observability Infrastructure (distributed tracing, metrics, logs)
└─ Configuration Management (system config, contract registry, policy versions)

TIER 1: INGESTION & NORMALIZATION
├─ Discovery Engine (data collection, normalization, validation)
└─ Integration Hub (external API abstractions, credential management)

TIER 2: INTELLIGENCE & REASONING
├─ Knowledge Engine (graph + semantic + versioned state management)
├─ Analysis Engine (AI-powered reasoning: research, hypothesis, risk assessment)
├─ Simulation Engine (scenario generation, monte carlo, historical replay)
└─ Learning Engine (calibration, attribution, performance evaluation)

TIER 3: ORCHESTRATION & EXECUTION
├─ Decision Router (zone classification, approval workflow routing)
├─ Execution Controller (idempotent external actions, resource locking)
└─ Interface Adapters (Telegram bot, future API endpoints)

CROSS-CUTTING: GOVERNANCE
├─ Policy Enforcement (validation functions invoked by all tiers)
├─ Approval Workflows (human-in-the-loop for Hybrid/Human zones)
├─ Audit Trail (immutable logging of all governed actions)
└─ Override Mechanisms (emergency pause, cooldown-and-reconfirm)
Data Flow Direction:

Tiers enforce unidirectional data flow with explicit backpressure mechanisms:

text

External Sources → Tier 1 (Ingestion) → Tier 2 (Intelligence) → Tier 3 (Orchestration) → External Actions
                        ↓                       ↓                       ↓
                   Event Bus ←────────────────────────────────────────┘
                        ↓
                   Governance (validates at each tier boundary)
Tier Separation Rules:

The following patterns are architecturally prohibited:

Tier 3 components MUST NOT directly query Tier 1 tables (bypass via Event Bus required)
Tier 2 components MUST NOT call external APIs directly (MUST route through Tier 1 Integration Hub)
Any tier MUST NOT modify Governance policies (self-governance prohibited; human operator exclusive authority)
Governance MUST NOT invoke downstream workflow execution (prevents circular dependency per Governance Invariant)
No engine MAY directly access another engine's private internal tables (shared access only through explicitly documented public contracts)
Tier Separation Enforcement:

Tier boundaries are enforced at multiple levels to prevent architectural drift:

Database Level:

Role-based access control assigns read/write permissions per tier
Tier 1 roles: Read/write access to raw data tables only
Tier 2 roles: Read-only access to normalized views, no raw table modification
Tier 3 roles: No direct database access except governance/audit tables
Row-level security policies MUST be activated in production environments (development MAY disable for rapid iteration, but production REQUIRES defense-in-depth enforcement)
Workflow Orchestration Level:

Tier 1 workflows: Credential access to external APIs; Event Bus write access; NO AI Gateway access
Tier 2 workflows: AI Gateway access; Event Bus read access; NO external API credentials
Tier 3 workflows: External execution API access; NO data collection API access
Contract Registry Level:

Every cross-tier call MUST be declared in contract registry
Runtime validation: Before workflow invocation, verify contract registry permission
Violations logged to architecture compliance system and rejected
Compile-Time Validation:

Pre-deployment: Schema analyzer scans workflow definitions for direct table access
Reject deployment if workflow accesses tables outside its tier permission scope
Prevent tier violations before production deployment
Defense-in-Depth Principle:

Tier separation relies on multiple enforcement layers rather than single point of control. This architectural principle ensures that:

Accidental tier violations are caught during development (compile-time validation)
Intentional violations are blocked at runtime (contract registry, role permissions)
Malicious violations trigger immediate alerts (row-level security, audit trail)
No single enforcement failure compromises architectural integrity
2.2 Event Bus Architecture
The Event Bus is the exclusive inter-tier and inter-engine communication mechanism, implemented as a durable message backbone with guaranteed delivery semantics.

Delivery Guarantee Model:

AHOS Event Bus provides At-Least-Once Delivery combined with Idempotent Processing. This design is intentional and production-safe:

At-Least-Once: The system guarantees every published event will be delivered to subscribed consumers at least one time. Under failure conditions (consumer crashes, network partitions, database failover), events MAY be delivered multiple times.

Idempotent Processing: All consumers MUST implement idempotent handlers. Duplicate event reception is expected and handled via idempotency keys. Consumers detect duplicates and process each logical event exactly once despite potentially receiving the same event multiple times.

Rationale for At-Least-Once (Not Exactly-Once):

Exactly-once delivery requires distributed coordination (two-phase commit across Event Bus and all consumers), introducing:

Higher latency (synchronous coordination overhead)
Lower availability (coordination failure blocks entire pipeline)
Increased complexity (distributed transaction management)
At-Least-Once with idempotency achieves the same correctness guarantee (each event processed exactly once) with:

Lower latency (asynchronous publish, consumers dedup locally)
Higher availability (independent consumer failure handling)
Simpler implementation (database-level uniqueness constraints)
This is a standard pattern in production event-driven architectures.

2.2.1 Delivery Mechanism
Hybrid Push-Pull Model:

The Event Bus employs a low-latency push notification mechanism with polling fallback for reliability:

Primary Path (Push Notification):

Event published: Durable write to Event Bus with assigned monotonic sequence number
Notification sent: Best-effort, non-blocking notification to active consumers
Consumers listening: Receive notification immediately (typical latency sub-second)
Consumer action: Query Event Bus for events beyond last processed sequence
Fallback Path (Polling):

All consumers poll Event Bus periodically regardless of notification receipt
Query: Same as push path (events beyond last processed sequence)
Process events in sequence number ascending order
Update consumer checkpoint after successful processing
Rationale for Hybrid Approach:

Push notifications provide low latency but have failure modes that polling covers:

Failure Mode	Impact Without Polling	Mitigation via Polling
Notification loss during consumer restart	Consumer crashes; notifications sent during downtime lost; events never processed	Consumer restart triggers immediate poll; catches all missed events
Connection pool interference	Notification requires persistent connection; pool may close idle connections	Regular polling detects missed events even if notification connection dropped
Thundering herd on burst	Large event bursts; notifications fire to all consumers simultaneously; resource saturation	Polling rate-limits wake-up frequency; natural backpressure
Notification payload limits	Notification mechanisms typically have payload size constraints	Polling fetches full event from durable storage; no size limit
Sequence Number Guarantees:

The Event Bus assigns monotonic sequence numbers providing global ordering with the following guarantees:

Global Monotonicity: Sequence numbers MUST be strictly increasing across all events
No Reuse: Sequence numbers MUST NEVER be reused, even after database restore or migration
Gap Tolerance: Gaps in sequence numbers are normal and acceptable (rolled-back transactions, concurrent inserts, compliance-mandated deletions)
Ordering Dependence: Event ordering depends solely on monotonic increase of sequence numbers, not on absence of gaps
Gap Detection & Recovery:

Consumers detect and handle sequence number gaps to ensure completeness:

Consumer processes event with sequence N
Next available event has sequence N+5 (gap detected: N+1 through N+4 missing)
Wait period: Consumer waits configurable duration (allows late-arriving events to appear)
Gap persistence check: After wait period, query explicitly for missing range
Recovery paths:
If events found: Process in order, update checkpoint, continue
If events truly missing: Log to gap registry, alert operator, advance checkpoint past gap (do not block stream indefinitely)
Gap Handling Trade-off:

Advancing past unrecoverable gaps prioritizes stream availability over strict completeness. This is acceptable because:

Permanent gaps are rare (database corruption or manual deletion required)
Alternative (block stream until gap resolved) halts all downstream processing indefinitely
Gap events logged and retrievable for manual recovery
Critical events (governance, execution) monitored separately for completeness verification
Connection Health Monitoring:

Dedicated health-check mechanism runs periodically to verify Event Bus connectivity and automatically recover from connection interruptions.

2.2.2 Event Schema & Metadata
Standard Event Envelope:

Every event published to Event Bus MUST conform to a standard structure containing:

Core Identity:

Unique event identifier (globally unique, immutable)
Sequence number (monotonic, global ordering, system-assigned)
Idempotency key (category-specific uniqueness, see §2.2.3)
Event Classification:

Event type (namespaced: domain.entity.action)
Aggregate type (entity type affected)
Aggregate identifier (entity instance)
Payload:

Event-specific data (schema validated against contract registry)
Metadata:

Correlation identifier (request-scoped, maps to opportunity/analysis session)
Causation identifier (event causing this event, null for root)
Causal depth (hops from root event, 0 for root)
Trace identifier (distributed tracing root)
Parent span identifier (distributed tracing parent operation)
Source service (producer identity)
Schema version (contract version)
Priority (critical | standard | background, for priority scheduling)
Timestamps:

Occurred at (when event happened in domain time)
Published by (producing workflow/component identity)
Received at (when Event Bus received event, system-generated)
Maximum Event Size:

Event payloads MUST NOT exceed a defined size limit (typically several hundred kilobytes) when serialized. This limit ensures:

Efficient network transmission
Reasonable storage overhead
Compatibility with notification mechanism limits
Large Payload Handling:

Events exceeding size limits MUST store payload externally:

Upload payload to object storage
Event payload contains metadata and reference only (location, size, hash, summary)
Consumers retrieve full payload from object storage when needed
Object storage retention aligned with Event Bus retention policy
Event Type Naming Convention:

Format: {domain}.{entity}.{action}

Naming MUST follow these rules:

Domain: Tier identifier (discovery, knowledge, analysis, decision, governance, execution)
Entity: Specific entity type (signal, entry, hypothesis, approval, action)
Action: Past-tense verb (created, updated, versioned, approved, executed)
Examples:

discovery.signal.ingested (Tier 1: raw signal received)
knowledge.entry.created (Tier 2: new knowledge entry)
knowledge.entry.versioned (Tier 2: knowledge entry updated with new version)
hypothesis.status.updated (Tier 2: hypothesis lifecycle transition)
decision.approval.granted (Governance: human approval recorded)
governance.override.executed (Governance: emergency override invoked)
execution.action.completed (Tier 3: external action finished)
Metadata Field Semantics:

correlation_id:

Purpose: Groups all events related to single opportunity or analysis session
Scope: Single opportunity lifecycle (discovery → analysis → decision → execution)
Used for: Trace reconstruction, cost attribution, lineage tracking, scatter-gather coordination
causation_id:

Purpose: Points to immediate parent event in causal chain
Scope: Direct cause-effect relationship (not transitive)
Used for: Happens-before relationship tracking, dependency resolution, causal chain reconstruction
Null value: Root events (no causal parent) have null causation identifier
causal_depth:

Purpose: Counts hops from root event
Scope: Entire causal chain
Used for: Detecting infinite loops (depth exceeding threshold triggers investigation), visualizing dependency depth
Assignment: Root events depth=0; child events parent_depth + 1
schema_version:

Purpose: Contract version identifier for payload structure
Scope: Event type schema evolution
Used for: Consumer compatibility checking, schema migration coordination
priority:

Purpose: Event prioritization for resource-constrained processing
Scope: Consumer scheduling decisions
Values: critical (immediate processing required), standard (normal priority), background (defer if resources constrained)
Contract Validation (Pre-Publication):

Before event insertion into Event Bus, schema validation MUST occur:

Lookup contract from contract registry
Validate payload against schema definition
If validation fails: Log error, reject publication, route to malformed event queue
If validation succeeds: Proceed with publication
Contract Version Compatibility:

The contract registry defines compatibility ranges for each event type:

Current version (active schema)
Minimum supported version (oldest version still accepted)
Maximum supported version (newest version understood)
Status (active, deprecated, superseded)
Consumer Compatibility Validation:

Before processing event, consumer MUST validate schema version compatibility:

Event version below minimum supported: Reject or transform via compatibility shim
Event version above maximum supported: Route to dead letter queue for consumer upgrade
Event version within range: Process normally
Contract Evolution Policy:

Schema changes are classified by compatibility impact:

Backward-Compatible Changes:

Adding optional fields to payload
Adding new enum values (if consumer handles unknown values gracefully)
Relaxing validation constraints
Deployment Expectation: Consumers continue processing events; new fields ignored until consumer upgraded.

Forward-Compatible Changes:

Removing deprecated optional fields (after deprecation period)
Tightening validation constraints on new events (existing events grandfathered)
Deployment Expectation: Producers begin emitting new schema; old consumers continue functioning.

Breaking Changes:

Removing required fields
Changing field types
Renaming fields
Adding required fields without defaults
Deployment Expectation: Requires coordinated deployment (deploy consumers first supporting dual-schema, then producers, then update minimum supported version).

Breaking changes MUST be avoided where possible; use expand-contract pattern (add new field, deprecate old field, remove old field in separate version increments).

2.2.3 Event Schema Migration Strategy
Purpose:

AHOS Event Bus contains historical events across years of operation. Schema migrations MUST occur without downtime, without data loss, and with full backward compatibility during transition periods.

Migration Types:

Migration Type	Definition	Downtime Required	Complexity
Online Migration	Schema change applied while system running; dual-schema support during transition	None	Moderate to High
Offline Migration	System paused; batch transformation applied; system resumed with new schema	Hours to Days (unacceptable for production)	Low
Batch Migration	Historical events transformed incrementally in background; new events use new schema immediately	None	High
AHOS Selection: Online Migration with Batch Historical Transformation (combines zero-downtime with full historical consistency).

Online Migration Workflow:

Phase 1: Preparation & Validation

Contract Proposal: New schema version drafted with status 'proposed'
Transformation Logic Development: Write bidirectional transformation functions
Validation in Staging: Deploy transformation logic; replay sample production events; verify correctness
Governance Approval: Submit schema migration to approval workflow (requires ADR documenting rationale, impact analysis, rollback plan)
Phase 2: Dual-Schema Deployment
5. Activate Dual-Schema Mode: Mark contract as supporting both old and new versions
6. Consumer Deployment (Consumer-First Strategy): Deploy updated consumers supporting both schemas; validate correct processing
7. Producer Deployment: Deploy updated producers emitting new schema; validate new events

Phase 3: Historical Event Migration (Batch Transformation)
8. Batch Migration Job: Background process transforms historical events in batches
9. Migration Monitoring: Track progress, migrated events, failed events, status
10. Validation After Migration: Random sampling, schema validation, replay testing

Phase 4: Cutover & Cleanup
11. Update Minimum Supported Version: Mark old version as no longer supported
12. Retire Old Consumers: Deploy final consumer version supporting only new schema
13. Decommission Dual-Schema Mode: Mark contract as active with single version
14. Archival: Previous contract versions marked as superseded; retained for historical reference

Rollback Procedure:

If critical issues detected during migration:

Immediate Rollback (Before Batch Migration Completes):

Revert producers to emit old schema
Consumers already support old schema (dual-schema); no consumer rollback needed
Pause batch migration job
Revert migrated events using inverse transformation
Post-Cutover Rollback (After minimum version updated):

Not supported without downtime once old consumers decommissioned
Prevention: Dual-schema period MUST be long enough (30+ days) to detect issues before cutover
Migration Monitoring & Alerts:

System tracks:

Migration progress (percentage complete)
Failed event transformations
Estimated time remaining
Consumer compatibility status
Alert thresholds:

Failed events exceed acceptable limit: Alert developer
Migration progress stalled: Alert operator
Will not complete before cutover deadline: Alert architecture team
Safe Deployment Sequence:

For breaking changes requiring coordinated deployment:

Consumer-First: Always deploy consumers before producers
Dual-Write Period: Producers may temporarily emit both old and new schema events
Validation Window: Minimum observation period after consumer deployment before producer deployment
Gradual Producer Rollout: Deploy producers incrementally with monitoring between stages
Failure Recovery:

If batch migration job crashes mid-execution:

Resume from last successful batch (tracked via migration progress)
Idempotency: Re-processing already-migrated events is safe (transformation is idempotent)
Verification: Final validation step catches any events missed during crash recovery
2.2.4 Idempotency Strategy
Category-Specific Idempotency Keys:

The Event Bus employs different idempotency strategies based on event category, ensuring retries are safe while allowing legitimate re-emissions:

Category 1: State Mutations (Entity Lifecycle Events)

Applies to: knowledge.entry.created, knowledge.entry.versioned, hypothesis.status.updated, policy.version.created

Idempotency Key Formula: entity_type:entity_id:version_number

Rationale: Same entity version published twice is duplicate; different versions are legitimate evolution.

Category 2: Derived Computations (Analysis Results)

Applies to: risk.score.calculated, simulation.scenario.completed, recommendation.synthesized

Idempotency Key Formula: correlation_id:computation_type:input_hash

Where input_hash is deterministic hash of source entity versions.

Rationale: Recomputing identical inputs produces duplicate; different inputs require new computation.

Category 3: External Actions (Execution Commands)

Applies to: execution.action.approved, execution.order.placed, notification.telegram.sent

Idempotency Key Formula: action_type:decision_id

Rationale: Each decision produces at most one execution action; action identifier deterministically derived from decision.

Category 4: Observability Events (Metrics, Logs, Traces)

Applies to: system.metric.recorded, system.log.created, error.occurred

Idempotency Key Formula: None (no deduplication at write time)

Rationale: Observability events are append-only; slight duplication acceptable; deduplication occurs at query time if needed.

Category 5: Compensation Events

Applies to: All events with compensation semantic (*.abandoned, *.invalidated, *.released, *.cancelled, *.rolled_back)

Idempotency Key Formula: entity_type:entity_id:compensation_type:workflow_id

Rationale: Same entity may be compensated by multiple workflows (if entity shared across workflows). Entity+compensation_type alone insufficient (would block second workflow's legitimate compensation). Workflow_id ensures each workflow's compensation attempt is distinct event, but retries within same workflow are deduplicated.

Example:

text

Workflow W1 fails → Attempts to abandon knowledge.entry.K123
  idempotency_key = "knowledge_entry:K123:abandoned:W1"

Workflow W2 also fails → Also attempts to abandon same knowledge.entry.K123
  idempotency_key = "knowledge_entry:K123:abandoned:W2"
  ACCEPTED (different workflow, legitimate duplicate compensation)

Workflow W1 retries compensation (transient failure)
  idempotency_key = "knowledge_entry:K123:abandoned:W1"
  REJECTED (same workflow, duplicate retry)
Idempotent compensation logic (§2.9) ensures multiple compensation attempts safe:

W1 compensation sets status='abandoned'
W2 compensation checks status, already 'abandoned', no-op
Final state correct regardless of execution order
Collision Handling:

On publication attempt with existing idempotency key:

No new event created (conflict prevents duplicate)
Existing event returned to caller (same result as if new event created)
No side effects triggered (consumers already processed original event)
Metrics counter incremented: event_bus.duplicate_prevented
Idempotency Key Collision with Failed Events:

If existing event with matching idempotency key is in dead letter queue:

Permanently Failed:

Do NOT retry automatically
Human investigation required
Raise error indicating manual resolution needed
Escalate to operator
Pending Retry:

Dead letter queue will retry existing event
Do not create duplicate
Return existing event identifier with status 'queued_for_retry'
Manually Resolved:

Prior failure was resolved
Allow new attempt
Mark as potential duplicate for monitoring
Log warning for investigation
Normal Case (Successful):

Return existing event identifier
Consumer already processed
No action needed
This ensures at-most-once event publication while supporting unlimited retries.

2.2.5 Backpressure & Consumer Rate Limiting
Problem Addressed:

Event bursts (large number of qualified candidates during high-activity periods) can overwhelm consumers if processed without limits, exhausting:

AI budget (multiple concurrent analyses exceeding daily allocation)
Database connections (concurrent queries saturating connection pool)
External API quotas (simultaneous requests exceeding rate limits)
Solution: Durable Backpressure via Pull-Based Consumption

Consumer Configuration:

Each consumer registered in Event Bus with:

Subscriber identifier
Event pattern (which events to consume)
Maximum concurrent invocations (concurrency limit)
Last processed sequence (checkpoint)
Status (active, paused, error)
Pull-Based Consumption Protocol:

Step 1: Query Available Events (Respecting Concurrency Limit)

Consumer queries Event Bus for events to process:

Calculate current in-flight count (events consumer is processing but not yet completed)
Query events beyond last processed sequence matching event pattern
Limit results to (max_concurrent - in_flight_count)
Order by priority then sequence number
Step 2: Claim Events Atomically with Lease

For each event fetched, consumer attempts atomic claim with renewable lease:

Attempt atomic update setting consumer identifier and lease expiration
If another consumer already claimed or lease not expired: Skip event
If successful: Proceed to process
Renewable Lease for Long-Running Operations:

Consumers processing long-running events MUST periodically renew lease:

Initial lease: Configurable duration (typically minutes)
Renewal interval: Before lease expiration (typically half lease duration)
Maximum lease duration: Hard timeout indicating stuck processing
Lease Renewal Protocol:

Consumer background thread renews lease for active events before expiration. This prevents lease reclamation during legitimate long operations.

Watchdog Lease Reclamation:

Watchdog job reclaims expired leases only (does not interrupt actively-renewed leases):

Periodically scan for events with expired leases
Clear consumer claim
Increment retry count
Make event available for other consumers
Alert if same event reclaimed repeatedly (route to dead letter queue)
Step 3: Process Event

Consumer invokes workflow to handle event. Processing may take seconds to minutes depending on event type.

Step 4: Release Event on Completion

On successful processing:

Update consumer checkpoint to event sequence number
Clear event consumer claim
Mark event as processed
Clear lease
On processing failure:

Clear consumer claim
Increment retry count
Clear lease
If retry limit exceeded: Route to dead letter queue
Step 5: Backpressure Application

If in-flight count at maximum concurrent limit:

Consumer sleeps (does not pull new events)
Sleep duration aligned with polling interval
Retry query after sleep
Continue until in-flight count decreases below limit
Durable Queue Architecture:

This design uses Event Bus storage itself as the queue:

Durable: Events never lost (persisted, backed up, replicated)
Crash-safe: Consumer crash → lease expires → events available for other consumers
No dual storage: No separate volatile queue requiring consistency management
Priority Scheduling:

Events with critical priority are processed before standard/background events.

Priority Use Cases:

Critical: Governance events, emergency overrides, execution completions (immediate processing required)
Standard: Discovery, analysis, simulation events (normal workflow)
Background: Metrics collection, learning calibration, cleanup jobs (defer if resources constrained)
Load Shedding (Budget-Aware):

When AI budget constrained:

Check remaining budget before pulling events
If below threshold: Only pull critical priority events
Prevents budget exhaustion on low-priority background tasks
Preserves capacity for critical operations
Scatter-Gather Coordination:

For workflows requiring aggregation of multiple asynchronous outputs (e.g., Recommendation Synthesizer waiting for Research, Hypothesis, Risk, Simulation results):

Scatter-Gather State Management:

Coordinator tracks expected tasks, completed tasks, failed tasks
Timeout defines maximum wait duration
Gather trigger indicates all-or-quorum complete
Scatter-Gather Protocol:

Scatter Phase: Coordinator publishes multiple events with same correlation identifier
Task Completion: Each completing task updates scatter-gather state
Completion Detection: When all tasks complete (or timeout expires), trigger gather
Timeout Handling: If timeout expires before all tasks complete, proceed with partial results or fail based on quorum rules
Gather Decision Logic: Determine if minimum required tasks completed; proceed or escalate
Minimum Quorum:

Gather MAY proceed if minimum required tasks complete (e.g., research + risk), even if optional tasks (simulation) fail or timeout.

Partial Result Handling:

Gather result MUST include incomplete tasks field listing tasks that did not complete. Downstream consumers flag output as potentially incomplete.

Cancellation Rules:

If any required task fails permanently (not retriable), coordinator MAY cancel remaining in-flight tasks. Cancellation updates event status but does not interrupt already-started processing.

Fan-Out Limits:

Scatter-gather SHOULD NOT exceed reasonable parallel task limit (typically 10 tasks per correlation) to prevent excessive resource consumption. Exceeding limit requires explicit governance approval via ADR.

Future Scalability Path:

If scatter-gather requirements exceed architectural limits, options include:

Hierarchical coordination (coordinators managing sub-coordinators)
Streaming aggregation (process results as they arrive, not all-at-once)
Quorum-based gather (proceed after threshold percentage complete)
Implementation requires ADR approval documenting specific use case, scalability testing, and resource impact analysis.

2.2.6 Ordering Guarantees
Per-Stream Ordering (Within correlation_id):

Events sharing the same correlation identifier MUST be processed in sequence number ascending order.

Guarantee: Operations on the same opportunity occur sequentially (discovery → knowledge creation → analysis → decision).

Cross-Stream Ordering (Different correlation_ids):

Events with different correlation identifiers have no ordering guarantee unless explicitly linked via causation identifier.

Processing order could vary based on consumer scheduling; both orderings are valid absent explicit causality link.

Causal Ordering (Happens-Before Relationships):

Problem: Knowledge entry K1 updated (event E1, correlation K1). Separately, opportunity O1 analyzes using K1 (event E2, correlation O1). E2 SHOULD see updated K1, but per-stream ordering alone doesn't enforce this (different correlations).

Solution: Causality Tracking via causation_id

Event E2 declares dependency on E1 by referencing E1's identifier as causation parent.

Consumer Processing with Causality Check:

Before processing event E2:

Check if causal parent has been processed
If processed: Safe to process E2
If not processed: Defer E2, process other events, retry after delay
If causal parent missing after timeout: Handle based on event criticality
Missing Causal Parent Handling:

Two options based on event criticality:

Option A (Strict - for critical events):

Fail with missing causal parent error
Route to dependency dead letter queue
Escalate to human operator
Used for: Tier 3 execution events (cannot execute on potentially stale governance state)
Option B (Degraded - for non-critical events):

Process with potentially stale data
Log warning
Mark result as potentially inconsistent
Used for: Tier 2 analysis events (can analyze with available data, flag uncertainty in output)
Deadlock Prevention:

Causal chains MUST form Directed Acyclic Graph (DAG):

Forward-only references: Event cannot reference future event as causation parent (enforced: causation identifier MUST reference event with lower sequence number)
Maximum depth: Causal depth exceeding threshold triggers alert (potential infinite causal chain detected); manual investigation required
Version-Based Consistency (Simplified Alternative):

For most entity references, version-based consistency is simpler than full causality tracking:

Event payload includes specific entity version required. Consumer validates required version exists before processing. If version missing: defer event with timeout, then use same two options as causality timeout (strict vs degraded).

AHOS Selection:

Use version-based consistency for simple entity references (cleaner, easier to implement)
Use causation identifier for complex multi-step workflows requiring strict happens-before (e.g., simulation → recommendation → execution chain)
2.2.7 Dead Letter Queue (DLQ)
Purpose:

Capture failed events for investigation and recovery without blocking event stream processing.

Failure Classification & Routing:

Events route to category-specific dead letter sub-queues based on failure type:

DLQ Category	Failure Type	Retry Strategy	Max Retention	Example
Transient	Temporary infrastructure issues	Exponential backoff, limited retries	Short-term	Database deadlock, API timeout, network error
Malformed	Schema violation, parse error	No retry; developer alert	Medium-term	Invalid payload, missing required field, type mismatch
Logical	Business logic error	Hold until workflow version increments	Medium-term	Division by zero, constraint violation, impossible state
Dependency	Missing causal parent or entity	Recheck dependency periodically, timeout limit	Medium-term	Event references knowledge entry not yet created
Permanent	Unfixable error	Manual operator investigation only	Long-term	External API resource not found, unrecoverable corruption
Dead Letter Queue Responsibilities:

Each dead letter entry tracks:

Original event identifier
Subscriber identifier (which consumer failed)
Failure category
Failure reason and details (stack trace, context, retry history)
Failure timestamp
Retry count and next retry schedule
Final disposition (pending_retry, manually_resolved, permanently_failed, discarded_with_approval)
Resolution metadata (resolved by, resolution notes, timestamp)
Automatic DLQ Processing:

1. Transient Failures (Auto-Retry with Backoff):

Retry schedule uses exponential backoff (delays increase with each retry attempt). Maximum retry attempts enforced. If maximum exceeded, transition to permanent failure category and alert operator.

2. Dependency Failures (Periodic Recheck):

Periodically check if missing dependency now exists. If exists: retry original event. If timeout expires without resolution: escalate to operator and transition to permanent failure.

3. Logical Failures (Await Workflow Update):

Monitor workflow registry for version updates. When new version deployed for workflow that generated failure, retry affected events with new version. If successful: mark as resolved.

4. Malformed & Permanent Failures (Manual Only):

No automatic retry. Operator actions:

Malformed: Developer fixes schema, re-publishes event manually
Permanent: Operator investigates root cause, determines if event can be manually corrected or discarded
Poison Event Handling with Governance:

If event fails repeatedly across multiple categories (indicating systematic issue, not transient):

Mark as poison event
Permanent discard REQUIRES explicit human acknowledgement via approval workflow
Stream advancement ONLY after operator approval
All actions logged to audit trail
Event remains in Event Bus storage (only consumer position advances)
No Automatic Discard:

Poison events remain in dead letter queue until explicit operator decision. All discard actions auditable and reversible.

Trade-off:

Sacrifices stream continuity temporarily (operator must intervene) to preserve auditability (no automatic silent data loss). Acceptable because:

Poison events are rare with proper schema validation
Events remain in dead letter queue for manual recovery
Operator can analyze root cause before permanent discard decision
All actions fully logged to audit trail
DLQ Metrics & Monitoring:

System tracks:

Events in each dead letter category
Average retry counts
Time in dead letter queue
Resolution rates
Alert thresholds:

Malformed event count exceeds limit: Alert developer (schema issue)
Permanent failure count exceeds limit: Alert operator (systematic failure)
Average time in queue exceeds limit: Alert (processing backlog)
Poison Event Investigation:

When poison event detected, generate investigation report containing:

Event type and payload
Failure reason and details
Number of failed consumers (if >1, likely systemic issue)
Failure categories encountered
Similar events in time window
Investigation paths based on findings:

Multiple failed consumers: Schema incompatibility (fix schema, redeploy consumers)
Logical failures: Workflow bug (fix workflow logic, replay)
Burst of similar failures: Invalid data from source (fix data source, discard batch)
Timeout failures: Downstream dependency unavailable (check circuit breaker, scale limits)
2.2.8 Event Replay & State Reconstruction
Replay Capability:

The Event Bus supports reconstructing system state by replaying historical events, enabling disaster recovery, debugging, and audit verification.

Replay Modes:

Mode	Use Case	Event Filter	Target Environment	Safety
Full Replay	Disaster recovery, new environment bootstrap	All events from beginning	Isolated database instance	Requires operator approval (high-risk)
Subset Replay	Single entity state reconstruction	Specific aggregate type and identifier	Isolated database schema	Governance-gated
Time Window Replay	Point-in-time state inspection, audit verification	Events within time range	Read-only query environment	Safe (no writes)
Filtered Replay	Re-process specific event types (e.g., after workflow fix)	Event type pattern	Test/validation environment	Requires validation suite pass
Snapshot-Based Replay	Efficient large-scale replay	Events after last validated snapshot	Isolated environment	Requires snapshot validation
Replay Safety Requirements:

Idempotency MUST be enforced: Consumers MUST handle duplicate events gracefully (replay re-delivers already-processed events)

Isolated Environment MUST be used: Replay MUST NOT execute against production database (separate database instance OR separate schema within same instance)

Ordering MUST be preserved: Events replayed in sequence number ascending order within filtered set

Side effects MUST be controlled:

External API calls disabled (or routed to sandbox endpoints)
Notifications suppressed (no messages during replay)
Execution actions blocked (no real trades/transfers)
AI Non-Determinism Handling in Replay:

Challenge:

Replaying AI request event will generate DIFFERENT AI response (AI providers are non-deterministic even with fixed parameters).

Solution - Response Capture Mode:

System captures all AI responses during normal operation for potential replay use.

AI Response Snapshots:

Capture mechanism stores:

Request identifier
Original response payload
Response timestamp
Model used and configuration
Token usage
Snapshot purpose (replay, audit, training)
Replay Mode Options:

Mode	Behavior	Use Case
Snapshot Replay	Use captured responses, no AI calls	Exact state reconstruction, audit
Live Replay	Re-invoke AI providers, accept non-deterministic responses	Workflow validation with current models
Hybrid Replay	Use snapshots for critical decisions, live for non-critical	Balance accuracy and cost
Comparison Replay	Invoke AI AND compare to snapshot, flag divergence	Detect model drift, validate consistency
Replay Configuration:

Each replay session defines:

Replay mode (snapshot, live, hybrid, comparison)
AI response strategy (use_snapshot, regenerate, compare)
Cost budget (maximum cost for live replay)
Divergence threshold (for comparison mode: acceptable response difference percentage)
Rationale:

Current replay architecture assumes determinism (true for database events, false for AI events). Without snapshot capture, historical state reconstruction impossible. Audit/compliance requires ability to prove "what the AI said at decision time."

Snapshot-Based Replay Optimization:

For large-scale replays (millions of events), replaying from genesis (sequence 1) is prohibitively slow. Snapshot-based replay enables efficient reconstruction.

Replay Snapshot Management:

System maintains validated database snapshots at periodic intervals:

Snapshot timestamp
Last sequence number at snapshot time
Database backup location
Validation status (pending, validated, failed)
Validation hash (checksum of database state)
Snapshot Creation Protocol:

Trigger: Monthly automated job or on-demand operator request
Database Backup: Point-in-time backup created
Sequence Capture: Record maximum sequence number at backup time
Validation: Restore backup to isolated environment, run validation suite, compute state hash
Registration: Record validated snapshot in registry
Replay from Snapshot:

Select most recent snapshot before target timestamp
Restore database from snapshot backup location
Replay events: Query events beyond snapshot sequence up to target timestamp
Validate final state hash against expected (if replaying to known checkpoint)
Performance Rationale:

Full replay of millions of events: Hours. Snapshot replay (restore snapshot + replay incremental events): Minutes. Snapshots enable practical disaster recovery within recovery time objectives.

Replay Validation:

Post-replay, state SHOULD be verified against expected checkpoints by comparing replayed state to production snapshot. Identify mismatches for investigation.

Audit Trail Linkage:

Every event automatically generates corresponding audit trail entry. This ensures dual record:

Event Bus (for replay, state reconstruction)
Audit Trail (for compliance, immutable history)
Audit trail entries created via database trigger on event publication.

2.2.9 Event Bus Retention & Lifecycle Management
Retention Policy:

Event Bus data is managed through multi-tier retention lifecycle ensuring auditability while controlling storage costs:

Storage Tier	Duration	Characteristics	Purpose
Hot Storage	90 days	Full queryability, indexed, partitioned	Active event processing, recent replay, debugging
Warm Storage	1 year	Compressed partitions, reduced indexes, read-optimized	Audit queries, historical analysis, compliance investigations
Archive Storage	7 years	External object storage, query-on-demand	Long-term compliance retention, disaster recovery baseline
Purge	After 7 years	Permanent deletion with governance approval	Compliance with data retention limits
Lifecycle Transition Protocol:

Hot → Warm:

Monthly job detaches old partitions, reindexes for read optimization. Write-optimized indexes removed; read-optimized indexes created.

Warm → Archive:

Export partition to compressed format, upload to object storage with archival-class storage, register archive location with metadata (row count, checksum), drop hot storage partition (data preserved in archive).

Archive → Purge:

Governance-approved purge after retention expiry. Requires approval record via approval workflow. After approval, delete from archive. Log to audit trail.

Retention Exceptions:

Governance events: Events with governance domain retained indefinitely (no purge)
Audit trail events: All audit trail synchronization events retained indefinitely
Legal hold: Events under legal hold (compliance investigation) exempt from purge until hold released
Replay Capability Preservation:

Archived events remain replay-capable:

Retrieve archive from object storage
Decompress
Load into temporary table
Replay from temporary table (same protocol as normal replay)
Archive retrieval SLA: Object storage retrieval time (typically hours for archival-class storage) plus restore processing time.

Event Bus Scalability Evolution:

When Event Bus storage exceeds architectural scale limits (billions of rows), consider sharding by aggregate type or event type prefix:

Separate storage per domain (discovery events, knowledge events, analysis events, governance events, execution events)
Each shard maintains independent sequence number space
Global ordering relaxed to per-shard ordering
Trade-off:

Increased complexity vs. scalability. Requires ADR approval before implementation.

2.3 Distributed Concurrency Control
AHOS employs multiple concurrency control strategies to prevent race conditions, duplicate processing, and state corruption across distributed workers and asynchronous workflows.

2.3.1 Locking Strategies by Use Case
Optimistic Locking:

Used for entities with low contention where conflicts are rare.

Mechanism:

Version-based conflict detection. Each entity maintains version counter. Update attempts specify expected version. If actual version differs (concurrent modification occurred), update rejected.

Use cases:

Knowledge entry confidence updates (multiple consumers may recalculate; last-write wins acceptable)
Hypothesis status transitions (single workflow typically owns hypothesis lifecycle)
Configuration updates (rare, low-contention)
Advantages:

No lock acquisition overhead
No deadlock risk
High concurrency for read-heavy workloads
Disadvantages:

Retry required on conflict
Not suitable for high-contention resources
Pessimistic Locking:

Used for entities requiring exclusive access during modification.

Mechanism:

Exclusive lock acquisition via row-level locking. Transaction acquires lock before read. Lock held until transaction commits or rolls back. Other transactions attempting to acquire same lock wait or timeout.

Use cases:

Capital reservation for execution (prevents overdraft via concurrent actions)
Approval workflow state transitions (only one approver may approve at a time)
Critical configuration updates requiring exclusive access
Advantages:

Guaranteed exclusive access
No retry logic needed
Prevents all concurrent modifications
Disadvantages:

Lock contention under high load
Deadlock risk if multiple locks acquired
Reduced concurrency
Lease Locking (Distributed Time-Based Locks):

Used for coordinating work across multiple consumers in Event Bus.

Mechanism:

Time-bound exclusive claim. Consumer atomically claims event by setting consumer identifier and lease expiration timestamp. Lease renewable via periodic updates. Expired leases automatically reclaimed by watchdog.

Use cases:

Event Bus consumer coordination (prevent duplicate processing)
Long-running background jobs (prevent duplicate execution)
Distributed cron job coordination (only one instance executes)
Advantages:

Crash-safe (expired leases auto-reclaimed)
No explicit unlock needed (time-based expiration)
Supports long-running operations via renewal
Disadvantages:

Clock skew sensitivity (all nodes must have synchronized clocks)
Lease duration tuning required (too short: false reclamation; too long: slow recovery from crashes)
Advisory Locks (Application-Level Coordination):

Used for application-level coordination without table-level locking.

Mechanism:

Named locks acquired via database advisory lock mechanism. Lock identified by application-chosen key (typically hash of operation name). Lock scoped to transaction or session based on use case.

Use cases:

Singleton background jobs (only one instance should run system-wide)
Exclusive maintenance operations (e.g., graph compaction, metric aggregation)
Cross-table coordination without row-level locks
Advantages:

No table-level contention
Named locks (human-readable identifiers)
Transaction-scoped or session-scoped (flexible)
Disadvantages:

Not distributed (single-database only; does not span multiple database instances)
Requires explicit unlock (leaked locks if process crashes without cleanup)
2.3.2 Resource Lock Protocol (Execution Concurrency Control)
Purpose:

Prevent race conditions in concurrent execution requests competing for limited resources (capital, position slots, API quotas).

Resource Types:

Resource Type	Constraint	Example
capital	Total available capital for positions	Daily allocation limit
position_slot	Maximum concurrent open positions	Position count limit
api_quota	External API rate limits	Requests per minute to exchange API
Resource Lock Responsibilities:

System maintains resource lock registry tracking:

Lock identifier
Decision consuming resource
Resource type
Resource amount reserved
Lock acquisition timestamp
Release timestamp (null while locked)
Lock holder (workflow execution identifier)
Timeout timestamp
Lock Acquisition Protocol (Two-Phase Commit):

Phase 1: Reserve Resources (Atomic Check-and-Lock)

Begin transaction with serializable isolation
Calculate currently locked resources (sum of active reservations)
Calculate available resources (total allocation minus locked amount)
If sufficient resources available: Insert lock record (reserves resource), commit transaction
If insufficient resources: Rollback transaction, return error
Serializable isolation level ensures no other transaction can commit conflicting lock between availability check and lock insertion, eliminating race conditions.

Phase 2: Execute or Release

After acquiring lock:

If execution succeeds:

Release lock (set release timestamp)
Deduct actual resource consumption from portfolio
Lock merely reserved capacity; actual deduction occurs on success
If execution fails:

Release lock (set release timestamp)
No portfolio update; resource remains available
Reservation cancelled without consumption
Timeout Watchdog Responsibilities:

Prevents leaked locks from crashes by reclaiming expired leases.

Watchdog operates in two phases for critical resource cleanup:

Phase 1: Synchronous Resource Release (CRITICAL)

Watchdog has DIRECT authority to release expired resource locks without dependency on Event Bus:

Query resource locks WHERE release timestamp NULL AND timeout timestamp less than current time
For each expired lock: Update lock table directly (set release timestamp to current time)
Transaction commits → Resource guaranteed released
No dependency on Event Bus availability or consumer processing
Rationale:

Resource release is CRITICAL operation that MUST succeed even if Event Bus consumers unavailable. Direct database update ensures resource availability regardless of downstream component health.

Phase 2: Asynchronous Compensation Trigger (IMPORTANT)

After successful resource release, trigger workflow state cleanup:

Check if compensation event already published for this lock (query Event Bus for resource.lock.expired event with matching lock identifier)
If event NOT found: Publish resource.lock.expired event to Event Bus
If event exists: Skip (idempotent; avoid duplicate events)
Compensation workflow consumes event (when Event Bus consumers available)
Compensation workflow updates workflow execution state to FAILED
Compensation workflow marks associated artifacts as abandoned
Failure Mode Handling:

If watchdog crashes between Phase 1 and Phase 2:

Phase 1 already completed: Resource released (no leak) ✅
Phase 2 not executed: Compensation event not published
Next watchdog execution: Detects lock already released (Phase 1 idempotent), publishes event if missing (Phase 2 resumable)
Architectural Invariant:

Critical resource cleanup MUST NOT depend on Event Bus consumer availability or downstream event processing.

This ensures:

Resource leaks prevented even if Event Bus consumers down
Compensation can be deferred if Event Bus unavailable
System self-heals via watchdog without operator intervention
Idempotent operations safe to retry after crashes
Deadlock Prevention:

If multiple resources must be locked:

Acquire locks in deterministic order: Always lock capital → position_slot → api_quota (consistent ordering prevents circular wait)
Lock bundling: Acquire all required locks in single transaction (atomic all-or-nothing)
Timeout escape: If lock acquisition blocks beyond threshold, rollback and retry with exponential backoff
2.3.3 Conflict Detection & Recovery
Conflict Scenarios:

Scenario	Detection Method	Recovery Strategy
Duplicate Recommendation	Two Analysis workflows produce recommendations for same opportunity	Idempotency key on recommendations table; second insert rejected
Duplicate Simulation	Two workers initiate same simulation scenario	Optimistic lock via unique constraint; second attempt rejected
Duplicate Execution	Retry triggers duplicate execution attempt	Idempotency key on execution actions derived from decision identifier
Concurrent Knowledge Update	Two workflows update same knowledge entry	Optimistic locking via version field; conflict detected on update; retry with fresh read
Conflicting Approvals	Two operators attempt to approve same request	Pessimistic lock via row-level locking; second approver waits or timeout
Conflict Recovery Protocol:

Optimistic Lock Failure:

Re-read entity with latest version
Re-apply operation logic with fresh state
Retry operation with current version
Unique Constraint Violation:

Idempotency key collision indicates duplicate operation
Query existing record with matching idempotency key
Return existing record (operation already completed)
No retry needed
Resource Exhausted:

Capital/quota unavailable
Do NOT retry immediately (would fail again)
Defer operation to queue with low priority
Retry when resource availability event received
Deadlock Detected:

Database detected deadlock (circular wait)
Rollback transaction automatically
Wait random jitter (prevents thundering herd)
Retry from beginning with fresh transaction
Unrecognized Conflict:

Log error for investigation
Escalate to human operator
Do not retry automatically (may cause harm)
Conflict Metrics:

System tracks conflict frequency by type:

Conflict type
Conflict count per time window
Average retry count per conflict
Alert if conflict rate exceeds threshold indicating high contention on resource. Recommend increasing concurrency limits or partitioning workload.

2.5 Circuit Breaker & Fault Isolation Architecture
Purpose:

Prevent cascading failures when external dependencies degrade. Circuit breaker pattern isolates failing components, preventing resource exhaustion from repeated failed attempts.

Circuit Breaker States:

text

CLOSED (normal) → OPEN (failing) → HALF_OPEN (testing recovery) → CLOSED
                      ↓
                  FORCED_OPEN (manual isolation)
State Semantics:

CLOSED (Normal Operation):

Requests pass through to dependency
Failure rate monitored
If failure threshold exceeded: Transition to OPEN
OPEN (Dependency Failing):

Requests immediately rejected without calling dependency
Fallback behavior invoked (cached data, degraded mode, error response)
After timeout period: Transition to HALF_OPEN
HALF_OPEN (Testing Recovery):

Limited requests allowed through (test if dependency recovered)
If test requests succeed: Transition to CLOSED
If test requests fail: Transition back to OPEN
FORCED_OPEN (Manual Isolation):

Operator manually opens circuit
Prevents all requests regardless of failure rate
Requires manual closure by operator
Used for: Planned maintenance, known dependency issues
Circuit Breaker Scope:

Scope	Trigger Condition	Impact When Open	Recovery Test
AI Provider (per-model)	Failure rate threshold OR timeout rate threshold within time window	Route to fallback model OR defer to background queue	Limited test requests at interval
External API (per-API)	Consecutive error threshold	Block requests, return cached data if available	Limited test requests at interval
Database Connection	Connection pool saturation threshold for duration	Reject non-critical queries, queue critical operations	Monitor pool recovery
Event Bus	Processing lag threshold (event count)	Throttle event publication rate	Monitor lag reduction
Circuit Breaker Registry:

System maintains circuit breaker state for each protected dependency:

Circuit identifier
Scope (ai_provider, external_api, database, event_bus)
Resource name (specific provider/API/component)
State (closed, open, half_open, forced_open)
Failure count
Last failure timestamp
Open timestamp
Next test timestamp
Manual override flag
Failure Detection:

Circuit breaker monitors each request to protected dependency:

Record request outcome (success/failure)
Update failure count within sliding time window
Calculate failure rate
If failure rate exceeds threshold: Open circuit
Opening Circuit:

When circuit opens:

Update state to OPEN
Record open timestamp
Calculate next test timestamp (open timestamp plus timeout duration)
Publish circuit opened event
Alert operator
Closed Circuit Behavior:

While circuit closed (normal operation):

All requests pass through to dependency
Failures recorded but do not block requests
Transition to open only if threshold exceeded
Open Circuit Behavior:

While circuit open (dependency failing):

Requests do NOT reach dependency
Immediate rejection with circuit open error
Fallback behavior invoked if available
Test requests attempted at interval
Fallback Strategies:

When circuit open, system may employ fallback depending on dependency type:

AI Provider Circuit Open:

Route to fallback model (different provider or model)
Defer request to background queue (process when circuit closes)
Return cached response (if applicable and recent)
Reject request with degraded mode indication
External API Circuit Open:

Return cached data (if available and acceptable staleness)
Return degraded response (limited functionality)
Reject request with retry-after indication
Database Connection Circuit Open:

Reject non-critical queries (metrics, background jobs)
Queue critical operations (governance, execution)
Scale connection pool if possible
Event Bus Circuit Open:

Throttle event publication rate
Defer non-critical events
Maintain critical event flow (governance, execution completion)
Half-Open Testing:

After timeout period expires:

Transition to HALF_OPEN state
Allow limited test requests through (typically 1-3 requests)
Monitor test request outcomes
If all succeed: Transition to CLOSED (dependency recovered)
If any fail: Transition back to OPEN (dependency still failing)
Manual Circuit Control:

Operators may manually control circuit state:

Force OPEN: Isolate dependency for planned maintenance
Force CLOSED: Override circuit for emergency access
Reset failure count: Clear accumulated failures after investigation
All manual actions require approval workflow and audit trail logging.

Integration with Event Bus:

Before publishing events to failing dependencies:

Check circuit breaker state for target dependency
If circuit open: Do NOT publish event to primary target
If fallback available: Publish fallback event, route to alternative
If no fallback: Defer event to background queue, return error
Circuit Breaker Metrics:

System tracks circuit breaker health:

Circuit state per dependency
Failure rate per dependency
Time spent in each state
Fallback invocation count
Alert thresholds:

Circuit open for extended duration: Alert operator (investigate root cause)
Frequent open/close transitions: Alert (flapping circuit, tune thresholds)
Multiple circuits open simultaneously: Alert (systemic issue, infrastructure problem)
Rationale:

Current architecture allows unlimited retry attempts to failing dependencies, causing:

Resource exhaustion (connection pools, thread pools)
Cascading failures (dependency failure spreads to dependent services)
Slow failure detection (timeout per request multiplied by retry count)
Circuit breaker provides:

Fast failure (immediate rejection when circuit open)
Resource protection (no connection attempts to known-failing dependency)
Automatic recovery testing (half-open state probes for recovery)
Graceful degradation (fallback behavior maintains partial functionality)
2.6 Failover & High Availability Architecture
Purpose:

Define failure modes, recovery paths, and continuity mechanisms ensuring AHOS remains operational during infrastructure failures.

Database Failover:

Failover Scenarios:

Scenario	Detection	Recovery Action	Expected RTO	Data Loss (RPO)
Primary database crash	Health check timeout	Auto-failover to standby replica	Sub-minute	Zero (synchronous replication)
Network partition	Connection pool exhaustion	Retry with exponential backoff, circuit breaker after threshold	N/A	Zero
Database connection leak	Pool saturation threshold	Force-close idle connections, scale pool, alert	Seconds	Zero
Replication lag	Standby lag threshold	Route read-only queries to primary (degraded mode), alert	N/A	Zero
Corruption (data integrity)	Constraint violation, checksum failure	Stop writes, restore from last validated snapshot, replay events forward	Hours	Up to last snapshot
Event Bus Continuity:

Push Notification Failure:

When push notification connection lost:

Polling fallback continues uninterrupted (already defined in §2.2.1)
No event loss (events durably stored in Event Bus)
Latency increase: Sub-second (push) → polling interval average (typically seconds)
Consumer Crash Recovery:

When consumer crashes mid-processing:

Event lease expires after timeout duration
Watchdog reclaims lease
Event becomes available for other consumers
Idempotency key prevents duplicate processing if crashed consumer already committed
Database Failover Impact on Event Bus:

After database failover to replica:

Push notification connections dropped (all consumers)
Consumers reconnect to new primary
Polling continues uninterrupted (queries work against new primary)
Consumer checkpoint preserved (stored in Event Bus)
Resume processing from last checkpoint
Split-Brain Prevention:

Event Bus does NOT require distributed consensus (single database instance is source of truth).

Database layer handles split-brain via:

Synchronous replication (primary waits for standby acknowledgment before commit)
Fencing (old primary prevented from accepting writes after failover)
Connection draining (graceful client migration to new primary)
AHOS components are stateless (no local state to reconcile after failover). All state persisted in database; failover transparent to application layer.

Recovery Time Objective (RTO):

Maximum acceptable downtime:

Database failover: Under 60 seconds (auto-failover, connection re-establishment)
Event Bus: Zero (polling-based, no downtime)
Consumer restart: Under 5 minutes (container orchestration restart)
Recovery Point Objective (RPO):

Maximum acceptable data loss:

Database: Zero (synchronous replication)
Event Bus: Zero (durable storage, no volatile queues)
Audit Trail: Zero (written synchronously with event publication)
Disaster Recovery:

In catastrophic failure scenarios:

Restore database from most recent validated snapshot
Restore Event Bus from most recent snapshot
Replay events from snapshot sequence forward
Validate state integrity
Resume normal operations
Maximum data loss: Time since last snapshot (typically hours, configurable based on snapshot frequency).

Sequence Number Preservation in Disaster Recovery:

When restoring database from backup:

Restore Event Bus table (includes last sequence number)
Reset sequence generator to maximum sequence number plus one
Verify no gaps created by restoration process
Failure to reset sequence will cause collision/reuse, violating architectural invariant.

Availability Targets:

Event Bus availability: 99.9% (under 9 hours downtime per year)
Database availability: 99.9% (auto-failover, redundancy)
End-to-end system availability: 99.5% (accounts for dependent service failures)
These targets assume proper infrastructure configuration (multi-zone deployment, automated failover, monitoring, alerting).

2.7 Knowledge Versioning Event Architecture
Purpose:

Knowledge versioning is AHOS's core differentiator. Event architecture must preserve knowledge evolution history, causality chains, and happens-before relationships.

Knowledge Versioning Event Pattern:

Event Type: knowledge.entry.versioned

Semantic Meaning: Knowledge entry has been updated with new version. This event announces creation of new version while preserving immutable history.

Payload Components:

Version Identity:

Version number (monotonically increasing per entry)
Parent version (immediate predecessor, null for initial version)
Version Type Classification:

confidence_update (confidence recalculated based on new evidence)
evidence_added (new supporting/contradicting evidence incorporated)
hypothesis_linked (hypothesis now references this knowledge)
contradiction_merged (conflicting knowledge reconciled)
Change Summary:

Confidence change (from value, to value)
Evidence count change (from count, to count)
Causative Context:

Hypothesis identifier (which hypothesis triggered this version, if applicable)
Branch Metadata:

Is branch flag (whether this is branched version)
Branch parent version (if branched, which version branched from)
Merge target version (if merging branches, which version merging into)
Metadata:

Correlation identifier (opportunity/analysis session)
Causation identifier (event causing this version creation)
Causal depth (hops from root event)
Schema version (contract version)
Causal Chain Reconstruction:

Knowledge versioning events MUST preserve happens-before relationships:

Example causal chain:

Hypothesis H456 confirmed (event E1)
Knowledge K123 version 5 created (event E2, causation_id = E1)
Recommendation R789 synthesized using K123:v5 (event E3, causation_id = E2)
Decision D012 approved (event E4, causation_id = E3)
Consumer Processing Rule:

Before processing event referencing specific knowledge entry version, consumer MUST verify:

Check if knowledge versioning event for required version has been processed
If processed: Safe to process current event
If not processed: Defer current event (causal parent not yet available)
If version event missing after timeout: Handle based on event criticality (strict vs degraded)
Knowledge Version Compaction Strategy:

Minor confidence updates (small delta) MAY be batched to reduce version proliferation:

Version created only if confidence delta exceeds threshold OR new evidence added
Micro-updates stored in lightweight confidence history side table
Periodic compaction merges micro-updates into new version when threshold crossed
Trade-off:

Reduces version proliferation vs. slight loss of granularity. Acceptable for production scale when knowledge entries referenced by hundreds of opportunities.

Projection:

Without compaction:

Knowledge entry K1 referenced by 100 opportunities
Each opportunity updates confidence → 100 versions of K1
After 1 year: Millions of knowledge versions (most trivial confidence deltas)
With compaction:

Only significant updates (confidence delta >5% OR new evidence) create version
Micro-updates tracked separately
Version count reduced by order of magnitude
Knowledge Branch Events:

When knowledge evolution requires exploration of alternative hypotheses (branching):

Event Type: knowledge.entry.branched

Payload:

Original entry identifier
Branch version number
Branch parent version (version from which branched)
Branch rationale
Branch owner (hypothesis or analysis driving branch)
Branch Merge Events:

When alternative knowledge branches reconcile:

Event Type: knowledge.entry.merged

Payload:

Target entry identifier
Source branch version
Target version (where merging into)
Merge strategy (conflict resolution approach)
Merged version number (result of merge)
Knowledge Versioning Scalability:

At scale (millions of knowledge entries, billions of versions over time):

Hot storage: Recent versions (90 days)
Warm storage: Historical versions (1 year)
Archive storage: Full version history (7 years)
Version queries optimized via partitioning by entry identifier and version number.

2.9 Workflow Compensation & Recovery Architecture
Purpose:

Multi-step workflows spanning minutes to hours may fail partially—some steps complete successfully while others encounter permanent failures. System MUST detect partial failures, release reserved resources, clean up intermediate artifacts, and maintain consistent state without operator intervention in the common case.

Architectural Principle: Best-Effort Idempotent Compensation

Compensation is NOT distributed transaction rollback or atomic undo. Compensation is best-effort cleanup with the following guarantees:

Idempotency: Every compensation action MUST be safely repeatable. Executing compensation twice produces same result as executing once.

Best-Effort: System attempts all applicable compensations. If individual compensation fails, system continues with remaining compensations rather than halting entire cleanup process.

Audit Preservation: Compensation NEVER deletes business data. All original events, intermediate artifacts, and compensation actions preserved in audit trail.

Resource Release: Compensation ALWAYS releases reserved resources (capital locks, AI budget reservations, execution resource locks) to prevent resource leaks.

State Consistency: After compensation completes, system state accurately reflects reality (workflow failed, resources available, artifacts marked appropriately).

Resource Cleanup Criticality Levels:

Resource cleanup operations are categorized by criticality to ensure proper failure handling:

CRITICAL (Synchronous, Fail-Safe):

Operations that MUST succeed to prevent resource leaks:

Resource lock release (capital, position slots, API quotas)
AI budget reservation release
Database connection release
Requirements:

MUST execute synchronously (complete before cleanup continues)
MUST NOT depend on Event Bus availability or consumer processing
MUST be idempotent (safe to execute multiple times)
MUST complete even if downstream components unavailable
Implementation:

Watchdog has DIRECT database update authority. Executes resource cleanup via direct database transactions without Event Bus dependency.

IMPORTANT (Asynchronous, Best-Effort):

Operations that SHOULD succeed for visibility but can be deferred:

Workflow state transition to FAILED
Opportunity state transition
Artifact status updates (mark as abandoned)
Audit trail logging
Requirements:

MAY execute asynchronously via Event Bus
MAY be deferred if Event Bus consumers unavailable
MUST be idempotent (late processing safe)
SHOULD complete eventually (when system recovers)
Implementation:

Event-driven via Event Bus. Compensation workflow consumes events when available.

Architectural Invariant:

Critical resource cleanup MUST NOT depend on Event Bus consumer availability or downstream event processing.

This ensures:

Resource leaks prevented even if Event Bus consumers down
System continues operating with degraded visibility (resources available, state updates deferred)
Full consistency restored when Event Bus consumers recover
No operator intervention required for temporary Event Bus unavailability
Compensation vs. Retry (Architectural Distinction):

Retry (Dead Letter Queue):

Purpose: Attempt same operation again expecting success
Trigger: Transient failure (temporary infrastructure issue, network timeout, rate limit)
Assumption: Underlying issue resolved; operation will succeed on retry
Outcome: Original operation completes successfully
Compensation:

Purpose: Undo effects of completed operations because downstream dependency failed
Trigger: Permanent failure (retry limit exhausted, workflow cancelled, timeout expired)
Assumption: Workflow cannot complete; cleanup required
Outcome: Partial work cleaned up; workflow marked failed
These are complementary patterns:

Step 2 fails transiently → Retry step 2 (DLQ handles this)
Step 2 fails permanently after exhausting retries → Compensate step 1 (this section handles this)
When Compensation Required:

Prefer retry over compensation. Compensation only when:

Failure is permanent (DLQ retry limit exceeded, moved to dlq_permanent)
Workflow explicitly cancelled (operator intervention, timeout watchdog)
Resource MUST be released (timeout expires, manual override)
Downstream step cannot proceed (missing required dependency after timeout)
Compensation Event Model:

Every state-mutating event that reserves resources or creates workflow artifacts SHOULD have corresponding compensation event type.

Compensation Event Pairs:

Forward Event	Creates/Reserves	Compensation Event	Compensation Action
knowledge.entry.created	Knowledge entry record	knowledge.entry.abandoned	Mark entry status as abandoned; exclude from active knowledge queries
hypothesis.created	Hypothesis record with linkages	hypothesis.abandoned	Mark hypothesis as invalid; clear knowledge entry linkages
execution.resource.locked	Capital/quota reservation	execution.resource.released	Release capital/quota reservation; make available for other workflows
ai.budget.reserved	Token budget reservation	ai.budget.released	Release token budget reservation; restore to available balance
opportunity.state.transitioned	State change in lifecycle	opportunity.state.rolled_back	Revert to previous state; record rollback reason and timestamp
simulation.scenario.started	Simulation execution context	simulation.scenario.cancelled	Mark scenario as cancelled; release computational resources
recommendation.synthesized	Recommendation record	recommendation.invalidated	Mark recommendation as invalid; prevent downstream execution
Design Principle: Logical Deletion, Not Physical Deletion

Compensation does NOT physically delete records from database. Compensation marks records with compensated/abandoned/invalid status.

Rationale:

Audit trail requires complete history (what was attempted, what succeeded, what compensated)
Compliance investigations need visibility into failures
Debugging requires access to intermediate artifacts
Learning from failures requires preserved context
Status Field Values for Compensated Entities:

Knowledge entries: status IN ('active', 'abandoned', 'superseded')
Hypotheses: status IN ('proposed', 'confirmed', 'rejected', 'abandoned')
Recommendations: status IN ('pending', 'approved', 'rejected', 'invalidated')
Simulations: status IN ('running', 'completed', 'failed', 'cancelled')
Queries for active entities filter by status. Compensated entities excluded from normal operations but remain queryable for audit purposes.

Compensation Policy Matrix:

Not all operations require compensation. Matrix defines compensation applicability:

Operation Type	Example	Compensatable?	Compensation Strategy	Rationale
Resource Reservation	Capital lock, AI budget reservation	✅ YES (REQUIRED)	Release reservation immediately	Prevents resource leaks; critical for system health
Workflow Artifact Creation	Knowledge entry, hypothesis, recommendation	✅ YES (RECOMMENDED)	Mark as abandoned/invalid	Clarifies workflow outcome; prevents confusion
External Read Operation	Fetch price data, query blockchain	❌ NO	None	Read-only; no side effects to compensate
External Write Operation	Execute trade, send notification	⚠️ DEPENDS	See External Action Execution Phase tracking	External systems may not support compensation
Audit Trail Write	Log event to audit_trail	❌ NO	None	Audit trail is append-only; never compensated
Metrics Recording	Record AI cost, processing latency	❌ NO	None	Observability data preserved regardless of workflow outcome
Knowledge Version Creation	Increment knowledge entry version	⚠️ CONDITIONAL	If version unused by other workflows: mark abandoned	Only compensate if version not referenced elsewhere
State Transition	Opportunity QUALIFIED → RESEARCHING	✅ YES (RECOMMENDED)	Rollback to previous state	Clarifies current workflow status
External Action Execution Phase Tracking:

External write operations (trades, notifications) require special handling during compensation:

Execution Phase	Compensation Strategy	Rationale
Before API call sent	Workflow failed before external action: Mark execution as cancelled; release resources; safe to compensate	No external side effect occurred
API call in-flight	Cannot determine if external system processed: DO NOT COMPENSATE automatically; mark execution as unknown; escalate to operator for manual reconciliation	Unknown state; automatic compensation may conflict with external system
API success received	External action completed: Compensation not applicable (cannot undo); retain execution record	External side effect already occurred; compensation cannot reverse
API failure received	External action did not occur: Safe to retry (via DLQ) or mark failed; release resources	No external side effect; safe to cleanup
External Action Execution State Tracking:

Workflow MUST track execution phase:

execution_phase = 'pending' (not yet started)
execution_phase = 'in_flight' (API call sent, no response)
execution_phase = 'completed' (success response received)
execution_phase = 'failed' (error response received)
Compensation logic:

If execution_phase = 'pending': Safe to cancel, mark as compensated
If execution_phase = 'in_flight': DO NOT compensate automatically, escalate to operator
If execution_phase IN ('completed', 'failed'): No compensation applicable
Policy Enforcement:

For each completed workflow step, system checks compensation policy matrix:

If compensation REQUIRED: Must execute before workflow marked as compensated
If compensation RECOMMENDED: Execute if possible; log warning if fails
If compensation CONDITIONAL: Evaluate condition; compensate only if condition met
If compensation not applicable: Skip; no action needed
Workflow Lifecycle Tracking:

System tracks multi-step workflow execution as distinct entity from individual events.

Workflow Execution Entity Responsibilities:

Workflow execution identifier (unique per workflow instance; typically opportunity correlation_id)
Workflow type (analysis, execution, learning, maintenance)
Expected steps (list of required operations in execution order)
Completed steps (which steps finished successfully with timestamps)
Failed steps (which steps encountered permanent errors with failure reasons)
Compensation steps (which compensation actions executed with results)
Lifecycle status (running, completed, failed, compensating, compensated, partially_compensated)
Started timestamp
Completed/Failed timestamp
Compensation started timestamp
Compensation completed timestamp
Workflow Lifecycle States:

text

RUNNING → COMPLETED (all steps succeeded)
        → FAILED (detected failure) → COMPENSATING (executing compensations)
                                    → COMPENSATED (all compensations succeeded)
                                    → PARTIALLY_COMPENSATED (some compensations failed)
State Definitions:

RUNNING:

Workflow actively executing steps
Some steps may be complete, others in-progress or pending
Resources may be reserved
Normal operational state
COMPLETED:

All expected steps finished successfully
No compensation needed
Resources released as part of normal completion
Terminal state (success)
FAILED:

At least one required step failed permanently (DLQ retry exhausted)
OR workflow timeout expired
OR operator cancelled workflow
Triggers transition to COMPENSATING
Non-terminal state (requires cleanup)
COMPENSATING:

System executing compensation actions for completed steps
Compensation workflow in-progress
Resources being released
Artifacts being marked as abandoned
Transient state (moving toward COMPENSATED)
COMPENSATED:

All applicable compensations executed successfully
Resources released
Artifacts marked appropriately
Workflow cleanup complete
Terminal state (failure with successful cleanup)
PARTIALLY_COMPENSATED:

Some compensations succeeded, others failed
Best-effort cleanup completed
Operator intervention required for manual resolution
Resources may still be locked (requires investigation)
Terminal state requiring manual review
Workflow Completion Detection:

After each step completes:

Update workflow execution state (mark step complete with timestamp)
Check if all expected steps complete
If all complete: Transition workflow to COMPLETED status
If any step failed and retries exhausted: Transition workflow to FAILED status
Workflow Timeout Detection:

Watchdog job scans workflow executions exceeding maximum duration:

Query workflows in RUNNING status where started timestamp plus max duration less than current time
For each timed-out workflow: Transition to FAILED status, trigger compensation
Alert operator with timeout summary

```
     └─────────┼─────────┘
               │
     ┌─────────▼─────────┐
```

**Sharding Strategy:**
- Hash-based sharding on memory ID
- Range-based sharding on temporal data
- Virtual nodes for balanced distribution
- Automatic rebalancing on node addition/removal

**Replication Strategy:**
- Primary-replica model for read scaling
- Quorum-based writes for consistency
- Eventual consistency acceptable for some operations
- Strong consistency required for state updates

#### 5.3.2 Vertical Scaling Considerations

**When to Scale Vertically:**
- LLM inference workloads (GPU memory requirements)

- Memory-intensive operations (graph algorithms)
- Latency-critical single-threaded operations

**Vertical Scaling Limits:**
- Document maximum feasible instance sizes
- Cost-benefit analysis thresholds
- Performance degradation points
- Migration strategy to horizontal scaling

#### 5.3.3 Autoscaling Policies

**Metric-Based Autoscaling:**
```
Target Metrics for Scaling Decisions:

1. CPU Utilization
   - Scale out: > 70% average over 5 minutes
   - Scale in: < 30% average over 15 minutes

2. Request Queue Depth
   - Scale out: > 100 queued requests
   - Scale in: < 10 queued requests for 10 minutes

3. Request Latency
   - Scale out: P95 latency > SLA threshold
   - Scale in: P95 latency < 50% of SLA for 20 minutes

   - Cognitive cycles per second
   - Memory retrieval latency
   - LLM token throughput
```

**Predictive Autoscaling:**
- Historical load pattern analysis

- Machine learning-based prediction models

**Scaling Constraints:**
- Minimum instance count (redundancy requirements)
- Maximum instance count (cost controls)
- Scaling velocity limits (prevent thrashing)
- Cooldown periods between scaling actions

#### 5.5.2 Circuit Breaker Pattern

**Circuit Breaker States:**

```
Circuit Breaker State Machine:

    ┌────────┐
    │ CLOSED │ (Normal operation)
    └───┬────┘
        │
        │ Error threshold exceeded
        ▼
    ┌────────┐
    │  OPEN  │ (Fail fast, no requests)
    └───┬────┘
        │
        │ Timeout period elapsed
        ▼
    ┌──────────┐
    │ HALF-OPEN│ (Test recovery)
    └─────┬────┘
          │
     ┌────┴────┐
     │         │
     ▼         ▼
  Success   Failure
     │         │
     ▼         ▼
  CLOSED     OPEN
```

**Circuit Breaker Configuration:**
- Error threshold: 50% error rate over 10 requests
- Timeout period: 30 seconds (OPEN state duration)
- Success threshold: 3 consecutive successes to close
- Volume threshold: Minimum 10 requests before evaluation

**Application to AHOS:**
- LLM API calls: Prevent cascading failures
- Database queries: Protect against connection storms
- External service calls: Isolate third-party failures
- Memory retrieval: Degrade gracefully when overloaded

**Resource Isolation Strategy:**

```
Thread Pool Bulkheads:

│         Request Handler Pool           │
│              (100 threads)             │
└────────────────────────────────────────┘
         │         │         │
    ┌────┴───┬─────┴───┬────┴────┐
    ▼        ▼         ▼         ▼
┌────────┐┌────────┐┌────────┐┌────────┐
│  LLM   ││ Memory ││ State  ││  API   │
│  Pool  ││  Pool  ││  Pool  ││  Pool  │
│ (40)   ││ (30)   ││ (20)   ││ (10)   │

```

**Bulkhead Benefits:**
- LLM processing failures don't block memory operations

- Guaranteed capacity for critical operations

#### 5.5.4 Retry and Backoff Strategies

**Exponential Backoff with Jitter:**

```
Retry Logic:

attempt = 0
max_attempts = 5
base_delay = 100ms

while attempt < max_attempts:
    try:
        result = operation()
        return result
    except RetryableError:
        attempt += 1
        if attempt >= max_attempts:
            raise
        
        # Exponential backoff: 100ms, 200ms, 400ms, 800ms, 1600ms
        delay = base_delay * (2 ** attempt)
        
        # Add jitter: ±25% random variation
        jitter = delay * (random() * 0.5 - 0.25)
        
        sleep(delay + jitter)
```

**Retry Policy by Operation Type:**

```
Operation Type: LLM Inference
├─ Retryable errors: Timeout, 503, GPU OOM
├─ Non-retryable: 400, 401, Invalid input
├─ Max retries: 3
├─ Base delay: 500ms
└─ Total timeout: 10 seconds

Operation Type: Memory Query
├─ Retryable errors: Connection lost, Timeout
├─ Non-retryable: Invalid query, Auth failure
├─ Max retries: 5
├─ Base delay: 100ms
└─ Total timeout: 5 seconds

Operation Type: State Write
├─ Retryable errors: Conflict, Timeout
├─ Non-retryable: Validation error
├─ Max retries: 10
├─ Base delay: 50ms
└─ Total timeout: 3 seconds
```

**Idempotency Requirements:**
All retry-able operations MUST be idempotent:
- Include request ID for deduplication
- Use conditional writes (compare-and-swap)
- Implement server-side deduplication windows
- Design for at-least-once delivery semantics

```
   └─ Per-instance capacity

4. Growth Projections
   ├─ User growth rate
   ├─ Feature expansion impact
   ├─ Seasonal variations
   └─ One-time events
```

**Capacity Calculation Formula:**

```
Required Capacity = (Peak RPS × Resource per Request) / 
                    (Instance Capacity × Target Utilization)

Where:
- Peak RPS: Maximum requests per second
- Resource per Request: CPU/Memory/GPU time needed
- Instance Capacity: Resources available per instance
- Target Utilization: Desired headroom (typically 70%)

Example:
Peak RPS = 1000
CPU per Request = 50ms
Instance Capacity = 4 cores × 1000ms = 4000ms/s
Target Utilization = 70%

Required Instances = (1000 × 50) / (4000 × 0.70)
                   = 50,000 / 2,800
                   = 18 instances
```

**Recovery Point Objective (RPO):**

**Recovery Time Objective (RTO):**
- Critical services: 30 minutes (automated failover)
- Core services: 2 hours (manual intervention)
- Non-critical services: 4 hours (standard recovery)
- Full system: 8 hours (disaster scenario)

#### 5.9.2 Disaster Recovery Plan

**DR Strategy: Multi-Region Active-Passive**

```
Primary Region (Active):
├─ 100% traffic
├─ Full read/write operations
├─ Continuous replication to DR region
└─ Health monitoring

Secondary Region (Passive):
├─ Infrastructure provisioned (warm standby)
├─ Database replicas (async replication)
├─ 0% traffic (DNS routing)
└─ Automated promotion capability

Disaster Triggers:
├─ Primary region outage (AWS region failure)
├─ Data center catastrophic failure
├─ Widespread network partition
├─ Security breach requiring isolation
└─ Manual activation (planned migration)
```

**Failover Process:**

```
Automated Failover (RTO: 30 minutes):

1. Detection (0-5 minutes)
   ├─ Multi-region health checks fail
   ├─ Automated failover triggered
   └─ Incident declared

2. Promotion (5-15 minutes)
   ├─ Secondary database promoted to primary
   ├─ DNS updated to secondary region
   ├─ Application instances started
   └─ Load balancers configured

3. Verification (15-25 minutes)
   ├─ Health checks passing
   ├─ Traffic flowing to secondary
   ├─ Data integrity verified
   └─ Functional testing

4. Monitoring (25-30 minutes)
   ├─ Error rate monitoring
   ├─ Performance validation
   ├─ User impact assessment
   └─ Communication sent
```

**Failback Process:**

```
Planned Failback (RTO: 4 hours):

1. Primary Region Recovery
   ├─ Infrastructure rebuilt/repaired
   ├─ Data synchronized from secondary
   ├─ Validation in isolation
   └─ Stakeholder approval

2. Reverse Replication
   ├─ Secondary becomes source of truth
   ├─ Primary catches up
   ├─ Replication lag minimized
   └─ Data consistency verified

3. Traffic Migration
   ├─ Canary traffic to primary (5%)
   ├─ Gradual increase (25%, 50%, 100%)
   ├─ Monitor each phase
   └─ Rollback plan ready

4. Secondary Demotion
   ├─ Stop accepting writes
   ├─ Resume passive replication role
   ├─ Return to warm standby
   └─ Post-failback validation
```

```

├─ 3xx: Redirection
│  ├─ 301 Moved Permanently: Resource relocated

├─ 4xx: Client Errors
│  ├─ 400 Bad Request: Validation error
│  ├─ 401 Unauthorized: Authentication required

│  ├─ 404 Not Found: Resource doesn't exist
│  ├─ 409 Conflict: Resource state conflict
│  ├─ 422 Unprocessable Entity: Semantic error
```

**Rate Limit Enforcement:**

```
Algorithm: Token Bucket

Implementation:
1. Each user has a bucket with N tokens
2. Bucket refills at rate R tokens/second
3. Each request consumes 1 token
4. Request allowed if ≥1 token available
5. Request rejected (429) if bucket empty

Distributed Rate Limiting:
├─ Redis-based counter (atomic increments)
├─ Sliding window algorithm
├─ Per-endpoint granularity
└─ Grace period for occasional bursts

Rate Limit Bypass:
├─ Whitelisted IP addresses (internal systems)
├─ Special header for trusted services
├─ Escalation process for temporary increases
└─ Audit log of bypass usage
```

### 8.4 Lessons Learned from Season 2

**What Worked Well:**

1. **ADR Process**
   - Forced thoughtful decision-making
   - Created invaluable documentation
   - Enabled onboarding and knowledge transfer
   - Prevented repeated debates

2. **Event-Driven Architecture**
   - Enabled loose coupling
   - Simplified integration patterns
   - Allowed independent scaling
   - Facilitated testing and debugging

3. **Observability-First Mindset**
   - Caught issues before users did
   - Enabled data-driven optimization
   - Reduced MTTR significantly
   - Built confidence in system health

4. **Incremental Rollout Strategies**
   - Canary deployments prevented major incidents
   - Blue-green enabled confident releases
   - Reduced risk of changes
   - Allowed rapid rollback when needed

5. **Cross-Functional Collaboration**
   - Architecture Review Board brought diverse perspectives
   - Security embedded early (not bolted on)
   - Operations input shaped resilient design
   - Product alignment ensured user value

**What Could Be Improved:**

1. **Earlier Performance Testing**
   - Some performance issues discovered late
   - Load testing should be continuous, not periodic
   - Synthetic monitoring needed earlier
   - Baseline metrics should be established upfront

2. **More Comprehensive Chaos Engineering**
   - Chaos experiments were reactive, not proactive
   - Should be integrated into regular testing
   - Need broader failure scenario coverage
   - Automated chaos testing desired

3. **Faster Feedback Loops**
   - Some architectural decisions took too long
   - Need lighter-weight decision process for reversible choices
   - Experimentation should be encouraged more
   - Fail fast, learn fast culture needed

4. **Better Capacity Modeling**
   - Initial capacity estimates were off
   - Need better tools for prediction
   - More rigorous load characterization required
   - Cost modeling should be more granular

5. **Clearer API Evolution Strategy**
   - Some API changes caused friction
   - Deprecation timeline should be stricter
   - Better communication to consumers needed
   - API design review should be mandatory
