1. Purpose
1.1 Objective
This document defines the Data Architecture for the AHOS (Adaptive Hypergraph Operating System), establishing the logical and physical data modeling principles, domain decomposition, storage strategies, and governance mechanisms that enable deterministic, auditable, and evolvable cryptocurrency intelligence operations.

The Data Architecture serves as the authoritative specification for all persistent state within AHOS, ensuring alignment with system-wide principles of immutability, versioning, traceability, and human governance supremacy.

1.2 Role Within AHOS
The Data Architecture operates as a foundational layer that supports:

Technical Architecture: Provides persistent state storage for all Tier 1, Tier 2, and Tier 3 engines as defined in the AHOS Technical Architecture.
Knowledge Architecture: Implements the storage substrate for knowledge entries, hypotheses, causal links, confidence decay modeling, and knowledge lifecycle governance.
Execution Model: Enables event sourcing, replay capability, idempotent execution, and deterministic state transitions.
Governance Framework: Ensures full auditability, immutable logging, approval tracking, and compliance with human override authority.

1.4 Authoritative Data Layer
Supabase (PostgreSQL) is designated as the single source of truth for all AHOS persistent state. All engines, workflows, and external integrations must treat Supabase as authoritative. No engine maintains independent persistent state outside this layer except for ephemeral runtime caches explicitly designed for performance optimization.

2. Data Architecture Principles
The following principles govern all data modeling, storage design, and schema evolution decisions within AHOS.

2.1 Single Source of Truth
Supabase (PostgreSQL) serves as the exclusive authoritative data store.
All persistent state resides in Supabase tables.
No distributed state across multiple database systems.
No shadow databases or replicated truth sources.
External caches (e.g., Redis) are ephemeral and must be rebuildable from Supabase.
2.2 Immutable-First Modeling
Operational records are append-only where feasible.
Modification of historical records is prohibited; corrections are represented as new versioned entries.
State transitions are captured as discrete events or version increments.
Deletions are implemented as soft deletes with deleted_at timestamps or status flags.
Immutable logs (audit trail, event bus) are never modified post-insertion.
2.3 Explicit State Management
All entities with lifecycle transitions maintain an explicit status field with enumerated values.
State transitions are logged as events or captured in versioned records.
No implicit state inference from absence of data.
State machine definitions are documented and enforced via database constraints or application logic.
2.4 Versioned Entities
Knowledge entries, hypotheses, policies, and configuration objects support explicit versioning.
Each version is stored as a separate row linked via parent_id or version_chain_id.
Version metadata includes:
version_number (integer, incrementing)
created_at (timestamp of version creation)
created_by (actor responsible for version)
superseded_at (timestamp when version became non-current)
is_current (boolean flag for active version)
2.5 Idempotent Keys
All write operations use idempotency keys to prevent duplicate execution.
Event insertion includes idempotency_key field (unique constraint).
Discovery ingestion uses deterministic content hashes as natural idempotency keys.
Retry-safe operations depend on unique constraints enforced at the database level.
2.6 Soft Delete Strategy
Deletion of user-facing entities (discoveries, knowledge entries, insights) is implemented via:
deleted_at timestamp (nullable)
status = 'deleted' enumeration value
Deleted records remain queryable for audit and compliance purposes.
Retention policies govern eventual archival or purging of soft-deleted records.
2.7 Time-Indexed Storage
All tables include:
created_at (timestamp with time zone, default now())
updated_at (timestamp with time zone, auto-updated via trigger)
Time-series data (metrics, logs, events) are partitioned by time ranges (daily or monthly).
Historical queries are optimized via composite indexes including created_at.
2.8 Multi-Tenant Ready
Schema design anticipates future multi-tenant deployment without requiring breaking changes.
All domain tables include optional tenant_id field (nullable in Phase 1, enforced in future phases).
Row-Level Security (RLS) policies are designed to filter by tenant_id when activated.
Single-tenant Phase 1 deployment operates with tenant_id = NULL or default value.
2.9 Row-Level Security Compatibility
All tables are designed to support PostgreSQL Row-Level Security (RLS).
RLS policies enforce:
Tenant isolation (when multi-tenancy is enabled)
Role-based access control (read-only vs. write roles)
Governance-controlled access (sensitive fields masked for non-admin roles)
RLS activation is governance-gated and phased per Strategic Master Plan.
2.10 Event Replay Capability
All state-changing operations are captured as events in event_bus.
Events include sufficient context to reconstruct state transitions.
Events are immutable and ordered by created_at and sequence_number.
System supports replay of event stream to restore state or test hypothetical scenarios.
2.11 Audit-First Design
All write operations are logged in audit_trail.
Audit entries include:
Actor (user, API key, or system component)
Entity type and entity ID
Operation type (create, update, delete, approve, override)
Before and after state (JSONB snapshot)
Timestamp and correlation ID
Audit trail is immutable and retained per compliance requirements.
3. Data Domain Decomposition
The AHOS data layer is logically decomposed into eight data domains, each with defined boundaries, ownership, and relationships.

3.1 Discovery Domain
Purpose: Stores raw signals, candidates, and structured discoveries ingested from external sources.

Key Entities:

discoveries: Normalized discovery records.
signals: Raw unprocessed signals from market data, on-chain events, social sentiment.
candidates: Intermediate candidates awaiting validation or enrichment.
Boundaries:

Owns all incoming data prior to knowledge extraction.
Does not store interpreted insights (Insight Domain responsibility).
Does not store validated knowledge (Knowledge Domain responsibility).
Relationships:

Feeds Knowledge Domain via extraction workflows.
Referenced by Hypothesis Domain for validation evidence.
Logged in Observability Domain for ingestion metrics.
3.2 Knowledge Domain
Purpose: Stores validated, versioned, and confidence-scored knowledge entries, hypotheses, and causal relationships.

Key Entities:

knowledge_entries: Structured knowledge records with confidence scores and decay modeling.
knowledge_versions: Immutable version history of knowledge entries.
hypotheses: Testable propositions derived from knowledge or generated by engines.
hypothesis_versions: Version history of hypotheses.
causal_links: Directed relationships between knowledge entries representing causal or correlational dependencies.
Boundaries:

Owns all validated knowledge and hypotheses.
Does not store raw discoveries (Discovery Domain responsibility).
Does not store simulation results (Simulation Domain responsibility).
Relationships:

Built from Discovery Domain data.
Referenced by Hypothesis Domain for testing.
Referenced by Decision Domain for action justification.
Governed by Governance Domain for approval and override.
3.3 Hypothesis Domain
Purpose: Stores hypotheses, testing protocols, validation outcomes, and branching logic for knowledge evolution.

Key Entities:

hypotheses: Core hypothesis records (shared with Knowledge Domain conceptually, but isolated for testing workflows).
hypothesis_tests: Test execution records linking hypotheses to validation workflows.
hypothesis_outcomes: Results of hypothesis validation (confirmed, refuted, indeterminate).
Boundaries:

Owns hypothesis lifecycle from generation to validation.
Does not own knowledge entries (Knowledge Domain responsibility).
Does not own predictive model performance (Learning Domain responsibility).
Relationships:

Consumes Discovery Domain data for validation.
Updates Knowledge Domain upon hypothesis confirmation.
Logged in Observability Domain for hypothesis test metrics.
3.4 Simulation Domain
Purpose: Stores simulation configurations, execution logs, and counterfactual scenario results.

Key Entities:

simulations: Simulation run metadata (scenario, parameters, execution timestamp).
simulation_results: Output records from simulation executions.
scenario_definitions: Reusable scenario templates for simulation.
Boundaries:

Owns all simulation execution state and outputs.
Does not store operational decisions (Decision Domain responsibility).
Does not store predictive model training data (Learning Domain responsibility).
Relationships:

References Knowledge Domain for input hypotheses and causal links.
Feeds Decision Domain with simulated outcomes for decision evaluation.
Logged in Observability Domain for simulation performance tracking.
3.5 Decision Domain
Purpose: Stores decisions, action logs, justifications, and execution outcomes.

Key Entities:

decisions: Decision records with rationale, confidence, and approval status.
actions: Executable actions derived from decisions.
action_executions: Logs of action execution attempts and results.
insights: Structured insights generated by Insight Engine (precursors to decisions).
Boundaries:

Owns all decision and action execution state.
Does not store hypotheses (Hypothesis Domain responsibility).
Does not store knowledge entries (Knowledge Domain responsibility).
Relationships:

Consumes Knowledge Domain and Simulation Domain for decision inputs.
Governed by Governance Domain for approval workflow.
Logged in Observability Domain for decision outcome tracking.
3.6 Governance Domain
Purpose: Stores approval workflows, override logs, policy versions, and human governance actions.

Key Entities:

approvals: Approval request records for decisions, actions, or policy changes.
override_log: Immutable log of human overrides to automated decisions.
policy_versions: Versioned governance policies and configuration rules.
Boundaries:

Owns all governance state and human intervention records.
Does not own operational decisions (Decision Domain responsibility).
Does not own audit trail (Observability Domain responsibility).
Relationships:

References Decision Domain for approval targets.
Enforces constraints on Knowledge Domain, Hypothesis Domain, and Decision Domain.
Logged in Observability Domain for governance event tracking.
3.7 Observability Domain
Purpose: Stores logs, metrics, traces, audit trail, and system health records.

Key Entities:

event_bus: Immutable event log for all state-changing operations.
audit_trail: Full audit log of user and system actions.
system_logs: Application and engine logs.
error_log: Structured error and exception records.
system_metrics: Time-series performance and operational metrics.
Boundaries:

Owns all observability and diagnostic data.
Does not store operational entities (owned by domain-specific tables).
Does not own governance policies (Governance Domain responsibility).
Relationships:

Receives events from all domains.
Provides diagnostic data to all engines and human operators.
Retained per compliance and retention policies.
3.8 Infrastructure Domain
Purpose: Stores system configuration, contract registry, ADR registry, and architectural compliance metadata.

Key Entities:

system_config: Key-value configuration store for system parameters.
contract_registry: Registry of API contracts, event schemas, and interface definitions.
adr_registry: Architectural Decision Records stored as database entries.
architecture_compliance: Compliance validation records for drift detection.
Boundaries:

Owns infrastructure metadata and architectural documentation.
Does not store operational data (owned by domain-specific tables).
Does not store logs or metrics (Observability Domain responsibility).
Relationships:

Referenced by all engines for configuration lookup.
Enforces schema compliance via contract validation.
Supports Architecture Review Layer via ADR and compliance records.
### 3.9 Domain–Tier Alignment Clarification

The data domains defined in this section represent logical storage boundaries only.

They do NOT redefine or replace the canonical Tier 0–3 engine decomposition defined in the AHOS Engineering Transition Roadmap.

Engine specifications remain authoritative for behavioral decomposition and runtime execution structure. Data domains exist solely to organize persistent storage and governance boundaries within the Supabase data layer.
4. Core Table Groups
This section defines the logical grouping of database tables, their purpose, key identifiers, and versioning logic. Physical schema definitions (DDL) are implementation artifacts; this section provides architectural intent.

4.1 Operational Tables
Purpose: Store active discoveries, signals, candidates, insights, and actions undergoing processing or execution.

4.1.1 discoveries
Purpose: Normalized discovery records post-validation and enrichment.

Key Fields:

id (UUID, primary key)
source (text, origin system or feed)
discovery_type (enum: signal, event, pattern, anomaly)
content (JSONB, structured payload)
confidence (numeric, 0.0–1.0)
status (enum: pending, validated, rejected, archived)
discovered_at (timestamp with time zone)
created_at (timestamp with time zone)
updated_at (timestamp with time zone)
deleted_at (timestamp with time zone, nullable)
Versioning: Not versioned; immutable post-validation. Status transitions logged in audit_trail.

Relationships:

Referenced by knowledge_entries via source_discovery_id.
Referenced by hypothesis_tests as validation evidence.
4.1.2 signals
Purpose: Raw unprocessed signals from ingestion pipelines.

Key Fields:

id (UUID, primary key)
source (text)
signal_type (enum: price, volume, social, on_chain)
raw_payload (JSONB)
ingested_at (timestamp with time zone)
processed (boolean, default false)
created_at (timestamp with time zone)
Versioning: Not versioned; append-only. Processed signals are soft-deleted or archived.

Relationships:

Feeds discoveries via Validator Engine processing.
4.1.3 candidates
Purpose: Intermediate candidates awaiting validation or enrichment.

Key Fields:

id (UUID, primary key)
source (text)
candidate_type (enum: hypothesis, insight, action)
payload (JSONB)
status (enum: pending, validated, rejected)
created_at (timestamp with time zone)
updated_at (timestamp with time zone)
Versioning: Not versioned; transient lifecycle.

Relationships:

Feeds hypotheses, insights, or actions upon validation.
4.1.4 insights
Purpose: Structured insights generated by Insight Engine, ready for decision evaluation.

Key Fields:

id (UUID, primary key)
insight_type (enum: opportunity, risk, trend, anomaly)
title (text)
description (text)
confidence (numeric, 0.0–1.0)
supporting_evidence (JSONB array of discovery IDs and knowledge entry IDs)
status (enum: active, actioned, dismissed, expired)
created_at (timestamp with time zone)
updated_at (timestamp with time zone)
expires_at (timestamp with time zone, nullable)
Versioning: Not versioned; lifecycle managed via status transitions.

Relationships:

Referenced by decisions as decision justification.
Referenced by actions for execution context.
4.1.5 actions
Purpose: Executable actions derived from decisions.

Key Fields:

id (UUID, primary key)
decision_id (UUID, foreign key to decisions)
action_type (enum: alert, trade, rebalance, report)
parameters (JSONB)
status (enum: pending_approval, approved, executed, failed, cancelled)
approval_required (boolean)
approved_by (UUID, nullable, references user or governance record)
approved_at (timestamp with time zone, nullable)
executed_at (timestamp with time zone, nullable)
created_at (timestamp with time zone)
updated_at (timestamp with time zone)
Versioning: Not versioned; lifecycle managed via status and execution logs.

Relationships:

Parent: decisions.id
Child: action_executions (execution attempt logs)
Governed by: approvals (if approval required)

### 4.2 Knowledge & Memory Tables

**Purpose:** Store validated knowledge entries, version history, hypotheses, hypothesis versions, and causal relationships between knowledge entities.

#### 4.2.1 `knowledge_entries`

**Purpose:** Canonical knowledge records representing validated facts, patterns, or models within the cryptocurrency intelligence domain.

**Key Fields:**
- `id` (UUID, primary key)
- `knowledge_type` (enum: fact, pattern, model, rule)
- `title` (text)
- `content` (JSONB, structured knowledge payload)
- `confidence_score` (numeric, 0.0–1.0, initial confidence upon creation)
- `current_confidence` (numeric, 0.0–1.0, decays over time per decay model)
- `decay_rate` (numeric, per-day decay factor)
- `last_validated_at` (timestamp with time zone)
- `validation_count` (integer, number of times re-validated)
- `status` (enum: draft, active, superseded, deprecated, expired)
- `aging_class` (enum: fresh, mature, stale, critical)
- `current_version_id` (UUID, references latest version in `knowledge_versions`)
- `source_discovery_ids` (JSONB array of UUIDs referencing source discoveries)
- `created_by` (text, engine or human actor identifier)
- `created_at` (timestamp with time zone)
- `updated_at` (timestamp with time zone)

**Versioning Logic:**
- Each mutation creates a new entry in `knowledge_versions`.
- `current_version_id` always points to the latest approved version.
- `is_current` flag on `knowledge_versions` determines active state.

**Relationships:**
- Parent/Child via `knowledge_versions.id` = `knowledge_entries.current_version_id`
- Referenced by `causal_links` (both as cause and effect)
- Referenced by `hypotheses` for testable proposition derivation

---

#### 4.2.2 `knowledge_versions`

**Purpose:** Immutable version history of each knowledge entry.

**Key Fields:**
- `id` (UUID, primary key)
- `knowledge_entry_id` (UUID, foreign key to `knowledge_entries`)
- `version_number` (integer, monotonically incrementing per knowledge entry)
- `content` (JSONB, full content snapshot of this version)
- `confidence_at_creation` (numeric)
- `change_summary` (text, description of changes from prior version)
- `superseded_by` (UUID, self-referencing FK to next version or NULL if current)
- `superseded_at` (timestamp with time zone, nullable)
- `is_current` (boolean, true only for active version)
- `created_by` (text)
- `created_at` (timestamp with time zone)

**Versioning Logic:**
- Insert-only; never updated or deleted.
- Only one record per `knowledge_entry_id` may have `is_current = true`.
- Enforced by database constraint or application-level transaction.
- Lineage traversable via `superseded_by` chain.

**Relationships:**
- Belongs to: `knowledge_entries`
- Self-referencing: `superseded_by` → next version's `id`

---

#### 4.2.3 `hypotheses`

**Purpose:** Testable propositions derived from knowledge entries or generated by engines requiring validation.

**Key Fields:**
- `id` (UUID, primary key)
- `hypothesis_type` (enum: directional, causal, correlational, pattern_continuation)
- `statement` (text, clear falsifiable statement)
- `context` (JSONB, supporting context, assumptions, scope)
- `status` (enum: proposed, testing, confirmed, refuted, indeterminate, retracted)
- `confidence_level` (numeric, 0.0–1.0 based on validation outcomes)
- `supporting_knowledge_ids` (JSONB array of UUIDs from `knowledge_entries`)
- `conflicting_knowledge_ids` (JSONB array of UUIDs)
- `test_protocol` (JSONB, defined test methodology)
- `test_outcome_summary` (text, aggregate result of all tests)
- `number_of_tests_run` (integer)
- `current_version_id` (UUID, references latest version in `hypothesis_versions`)
- `created_by` (text, engine or human originator)
- `created_at` (timestamp with time zone)
- `updated_at` (timestamp with time zone)
- `resolved_at` (timestamp with time zone, when status changed to terminal state)

**Versioning Logic:**
- Parallel to `knowledge_entries`: mutations create new `hypothesis_versions`.
- `current_version_id` tracks active version.

**Relationships:**
- References `knowledge_entries` via `supporting_knowledge_ids`
- Referenced by `hypothesis_tests`
- Versioned in `hypothesis_versions`

---

#### 4.2.4 `hypothesis_versions`

**Purpose:** Immutable version history of hypotheses (mirrors structure of `knowledge_versions`).

**Key Fields:**
- `id` (UUID, primary key)
- `hypothesis_id` (UUID, foreign key to `hypotheses`)
- `version_number` (integer)
- `statement` (text, hypothesis statement at this version)
- `context` (JSONB)
- `confidence_at_creation` (numeric)
- `change_rationale` (text)
- `superseded_by` (UUID, self-referencing)
- `superseded_at` (timestamp with time zone, nullable)
- `is_current` (boolean)
- `created_by` (text)
- `created_at` (timestamp with time zone)

**Versioning Logic:**
- Identical principles as `knowledge_versions`.

---

#### 4.2.5 `causal_links`

**Purpose:** Directed relationships between knowledge entries encoding causal, contributory, or dependency relationships.

**Key Fields:**
- `id` (UUID, primary key)
- `cause_knowledge_id` (UUID, foreign key to `knowledge_entries`)
- `effect_knowledge_id` (UUID, foreign key to `knowledge_entries`)
- `relationship_type` (enum: causes, contributes_to, enables, conflicts_with, reinforces)
- `strength` (numeric, 0.0–1.0, confidence in the relationship itself)
- `evidence_basis` (text, summary of evidence supporting this link)
- `status` (enum: active, weakened, broken, under_review)
- `established_at` (timestamp with time zone)
- `created_at` (timestamp with time zone)
- `updated_at` (timestamp with time zone)

**Versioning:**
- Not individually versioned; changes create new records.
- Broken links are soft-deleted via `status = 'broken'`.
- Knowledge graph evolution tracked via `audit_trail` and temporal queries on `updated_at`.

**Relationships:**
- Bidirectional relationship between two `knowledge_entries` records.
- Enables knowledge graph traversal and hypothesis generation.

### 4.3 Learning & Calibration Tables

**Purpose:** Store prediction outcomes, calibration metrics, model versions, and performance records enabling continuous learning and confidence modeling.

#### 4.3.1 `prediction_outcomes`

**Purpose:** Records of predictions made versus actual outcomes, forming basis for calibration.

**Key Fields:**
- `id` (UUID, primary key)
- `prediction_source` (text, engine or model identifier that generated prediction)
- `prediction_type` (enum: directional, magnitude, probability, categorical)
- `prediction_payload` (JSONB, what was predicted)
- `actual_outcome` (JSONB, what actually occurred)
- `outcome_observed_at` (timestamp with time zone)
- `prediction_horizon` (interval, time window prediction was made for)
- `accuracy_score` (numeric, calculated post-outcome observation)
- `calibration_error` (numeric, difference between predicted probability and observed frequency)
- `resolved` (boolean)
- `correlation_ids` (JSONB array of UUIDs linking to originating decision/action/event)
- `created_at` (timestamp with time zone)

**Versioning:** Not versioned; immutable outcome record.

**Relationships:**
- Aggregated into `calibration_metrics`
- Referenced by model evaluation workflows

---

#### 4.3.2 `calibration_metrics`

- `computed_at` (timestamp with time zone)

**Relationships:**

**Key Fields:**

**Relationships:**

#### 4.3.4 `performance_records`

**Key Fields:**

**Relationships:**

### 4.4 Infrastructure Tables

**Purpose:** Support system operation via event bus, subscriptions, logging, error handling, configuration management, contract registry, and architectural compliance.

#### 4.4.1 `event_bus`

**Purpose:** Central immutable event log capturing all state-changing operations across the system.

**Key Fields:**
- `id` (UUID, primary key)
- `event_type` (text, domain.event.action naming convention)
- `aggregate_type` (text, entity type affected)
- `aggregate_id` (UUID, entity ID affected)
- `payload` (JSONB, event-specific data)
- `metadata` (JSONB, correlation IDs, trace context, causation IDs)
- `sequence_number` (bigint, global ordering guarantee)
- `idempotency_key` (text, unique constraint for deduplication)
- `occurred_at` (timestamp with time zone)
- `published_by` (text, producing service or engine)
- `received_at` (timestamp with time zone)

**Constraints:**
- Unique constraint on `(idempotency_key)`.
- Non-null on required fields.
- No updates or deletes permitted after insertion.
- Indexes on `(event_type)`, `(aggregate_type, aggregate_id)`, `(occurred_at)`, `(sequence_number)`.

**Relationships:**
- Consumed by `event_subscriptions` for routing and processing.
- Source for audit trail reconstruction.

## 5. Versioning Strategy

### 5.1 Entity Versioning Model

AHOS employs a **side-table versioning model** for entities requiring historical lineage:

| Pattern | Applies To | Mechanism |
|---------|------------|-----------|
| **Full Snapshot Versioning** | `knowledge_entries`, `hypotheses`, `policies` | Current entity references active version; history stored in `{entity}_versions` table |
| **Append-Only Event Log** | All state changes | `event_bus` captures every mutation as immutable event |
| **Audit Trail Versioning** | All tables | `audit_trail` captures before/after states |
| **Immutable Records (No Versions)** | `signals`, `discoveries`, `predictions` | Records are logically immutable once committed |

### 5.2 Immutable Records vs. Version Records

**Immutable Records:**
- Written once, never modified.
- Errors corrected via supplementary correction records.
- Examples: `signals`, `discovery_events`, `audit_trail`, `event_bus`, `override_log`.

**Versioned Entities:**
- Main table holds "current head" pointer and computed aggregates.
- Version table holds full snapshot per version increment.
- Version creation triggered by explicit mutation or periodic re-validation.

**Decision Matrix for Versioning:**

| Criterion | Version Required? | Rationale |
|-----------|-------------------|-----------|
| Knowledge validity changes | Yes | Confidence updates, re-validation outcomes require lineage |
| Hypothesis refinement | Yes | Statement evolution, evidence addition require audit trail |
| Configuration changes | Yes (via `policy_versions`) | Rollback capability requires predecessor reference |
| Raw signal ingestion | No | Signals are immutable by nature |
| Operational logs | No | Append-only semantics sufficient |

### 5.3 Lineage Tracking

Lineage chains enable answering questions such as:

*"Why does this knowledge entry have confidence 0.87?"* → Trace through:
1. `knowledge_entries.current_confidence`
2. Most recent `knowledge_versions` entry showing update rationale
3. Linked `prediction_outcomes` feeding calibration
4. Original `discoveries` referenced in `source_discovery_ids`
5. Any `override_log` affecting intervening decisions

**Implementation:**
- `causal_links` provide direct graph edges between knowledge entries.
- `knowledge_versions.superseded_by` provides version-level forward chain.
- Event bus `metadata.causation_id` provides execution-level backward chain.
- Audit trail `correlation_id` provides cross-domain linkage.

### 5.4 Rollback Referencing

Rollback is supported **logically but not physically destructive**:

1. Identify target version from `knowledge_versions`.
2. Create NEW version copying content from rollback-target version.
3. Update `knowledge_entries.current_version_id` to point to newly-created copy.
4. Record rollback rationale in `audit_trail` and `event_bus`.
5. Old version history preserved; no data destruction.

**Prohibited Operations:**
- Never delete version records.
- Never mutate existing version records.
- Never set `is_current = false` without successor version existing.

### 5.5 Schema Evolution Principles

Schema evolution follows these rules:

1. **Additive Migrations Preferred**: New columns added via `ALTER TABLE ADD COLUMN`. New columns default to `NULL` or safe defaults.
2. **Non-Breaking Type Changes**: Widening columns (`VARCHAR(50)` → `VARCHAR(255)`) permitted without deprecation window.
3. **Breaking Changes Require Deprecation**: Column removal requires:
   - Minimum 30-day deprecation period with warnings.
   - Migration script preparing dependent systems.
   - Governance approval recorded in `approvals`.
   - ADR documenting change rationale.
4. **Enum Additions Only**: Enum types support adding values; removal requires deprecation period.
5. **Never Remove Tables Without Archival**: Table decommissioning triggers archival of all records to cold storage.

### 5.6 Migration Governance

All schema migrations MUST:

1. Be version-controlled in dedicated migrations directory.
2. Include forward and rollback scripts (rollback verified in staging).
3. Reference applicable ADR or approval record in header comment.
4. Pass `architecture_compliance` checks before deployment.
5. Be executed during maintenance windows with rollback plan documented.
6. Generate `event_bus` entry for schema modification audit trail.

## 6. Knowledge Lifecycle Modeling

### 6.1 Initial Validation Pathway

When a discovery emerges, the following lifecycle stages are modeled in the database:

```
Signal Ingestion → Discovery Creation → Knowledge Candidate → 
Hypothesis Generation → Validation Testing → Knowledge Entry Creation
```

**Database State Transitions:**

| Stage | Table(s) Affected | Status Values | Trigger Condition |
|-------|-------------------|---------------|-------------------|
| Signal Received | `signals.status` | `raw` | Ingestion event |
| Discovery Formed | `discoveries.status` | `pending` | Validator Engine extracts structure |
| Discovery Validated | `discoveries.status` | `validated` | Validation checks pass |
| Knowledge Candidate | `candidates.status` | `pending` | Insight Engine proposes knowledge entry |
| Knowledge Created | `knowledge_entries.status` | `draft` | Initial write to knowledge_entries + first version |
| Knowledge Published | `knowledge_entries.status` | `active` | Governance approval OR auto-publishing for low-confidence entries |
| Hypothesis Generated | `hypotheses.status` | `proposed` | Engine generates testable proposition |
| Hypothesis Tested | `hypotheses.status` | `testing` | Test protocol executed |
| Hypothesis Resolved | `hypotheses.status` | `confirmed` / `refuted` / `indeterminate` | Outcome determined |

### 6.2 Continuous Re-validation

Active knowledge entries undergo periodic re-validation:

1. **Scheduler Engine** identifies `knowledge_entries` where `now() - last_validated_at > revalidation_interval`.
2. **Re-validation Job** queries fresh `discoveries` and `signals` relevant to the knowledge entry.
3. **Outcome** generates new `prediction_outcome`-style validation record linked to `knowledge_entry_id`.
4. **Confidence Adjustment**:
   - If validation supports knowledge: `current_confidence` adjusted upward (capped at 1.0).
   - If validation contradicts knowledge: `current_confidence` adjusted downward.
   - Significant contradiction triggers `hypothesis` to investigate discrepancy.
5. **Version Update**: If confidence crosses threshold, new `knowledge_versions` created.

**Database Representation:**

```sql
-- Conceptual representation (implementation in PostgreSQL):
-- knowledge_entries includes re-validation scheduling fields
-- validation_outcomes table captures per-validation results
-- Links back to knowledge_entries for aggregation
```

### 6.3 Confidence Decay Modeling

Confidence naturally decays over time absent reinforcing validation:

**Decay Formula (Architectural):**
```
current_confidence(t) = base_confidence × e^(-λ × Δt)
```

Where:
- `λ` = `decay_rate` (stored per knowledge entry or defaulted from `system_config`)
- `Δt` = elapsed time since `last_validated_at`

**Database Implementation Approach:**
- **Option A (Computed)**: View or materialized view calculates live decayed value using `now()` minus `last_validated_at`.
- **Option B (Snapshot)**: Scheduler periodically writes decayed value to `current_confidence`; view reads cached value.
- **AHOS Selection**: Option B preferred for determinism; computed values introduce non-determinism in replay scenarios.

**Fields Supporting Decay:**
- `knowledge_entries.confidence_score`: Base confidence at last validation.
- `knowledge_entries.current_confidence`: Decay-adjusted confidence (refreshed by scheduler).
- `knowledge_entries.decay_rate`: Per-entry lambda parameter.
- `knowledge_entries.last_validated_at`: Anchor timestamp for decay calculation.
- `knowledge_entries.aging_class`: Derived classification bucket.

### 6.4 Aging Classification

Automatic aging classes categorize knowledge entries by staleness:

| Aging Class | Confidence Range | Time Since Last Validation | Allowed Actions |
|-------------|------------------|---------------------------|-----------------|
| **fresh** | > 0.8 | < 7 days | Full participation in reasoning |
| **mature** | 0.5 – 0.8 | 7 – 30 days | Participation with degraded weight |
| **stale** | 0.2 – 0.5 | 30 – 90 days | Limited participation; flags re-validation priority |
| **critical** | < 0.2 | > 90 days | Quarantined from automated decisions; alerts human analyst |

**Database Field:** `knowledge_entries.aging_class` (enum, computed by scheduler).

**Transition Rules:**
- Class can move *up* (via successful re-validation).
- Class can move *down* (via time passage or contradictory validation).
- Manual override possible via governance action (logged in `override_log`).

### 6.5 Branching Knowledge Versions

When a knowledge entry requires divergent evolution:

**Scenario Example:**
- Entry K1 exists (confidence 0.85, mature class).
- Conflicting validation suggests alternative interpretation.
- Human analyst or qualified engine initiates branch.

**Database Model:**

1. **Existing `knowledge_versions` chain continues unmodified.**
2. **New `knowledge_entries` record created** (K2) with:
   - `branch_parent_id` → K1's `current_version_id`
   - Own independent version chain starting at v1
   - Status starts as `draft` regardless of parent status
3. **Causal link created** in `causal_links`:
   - Relationship type: `branched_from`
   - Cause: K1 → Effect: K2
4. **Both branches coexist** until:
   - Branch confirmed superior → parent superseded, branch merges.
   - Branch refuted → branch marked deprecated.
   - Both remain valid alternatives → both persist as separate knowledge entries.

**Merging (when one branch supersedes):**
- Superseded entry gets `status = superseded`.
- Winning entry may absorb relevant portions into new version (documented in version rationale).

### 6.6 Knowledge Pruning vs. Archival

**Pruning (Soft Delete):**
- Applied when knowledge entry is definitively obsolete or incorrect.
- Operation: Set `knowledge_entries.status = deprecated` or `'deleted'`.
- Set `knowledge_entries.deleted_at = now()`.
- Retain in hot storage per retention policy (default: 12 months).

**Archival (Cold Storage):**
- Applied when hot-storage retention expires for deprecated/deleted knowledge.
- Operation: Move records to archival partition or external cold store (S3 Glacier, etc.).
- Keep lightweight stub in Supabase indicating archival location and retrieval key.
- Full restoration capability retained for regulatory or analysis needs.

**Pruning Triggers:**
- Explicit human governance decision (most common).
- Automated pruning of `critical` aging class exceeding maximum staleness threshold (governance-configurable, disabled by default).
- Regulatory obligation to remove specific information.

**Archival Boundaries (conceptual):**

| Data Category | Hot Storage Duration | Cold Storage Duration | Permanent Deletion |
|---------------|----------------------|----------------------|--------------------|
| Active Knowledge | Indefinite while active | N/A | Upon proper deprecation + retention expiry |
| Deprecated Knowledge | 12 months | 7 years | After 7 years (configurable) |
| Deleted Knowledge | 90 days | 3 years | After 3 years (configurable) |

### 6.7 Knowledge Graph Evolution

As knowledge entries are created, modified, pruned, branched, and archived, the knowledge graph evolves:

**Graph Structure in Database:**
- **Nodes**: `knowledge_entries` (plus `hypotheses` as provisional nodes).
- **Edges**: `causal_links` connecting nodes.
- **Node State**: Embedded in node properties (`status`, `confidence`, `aging_class`).
- **Edge State**: Embedded in edge properties (`status`, `strength`).

**Evolution Events Captured:**
1. Node creation → `event_bus` entry + `audit_trail` entry.
2. Edge creation → `causal_links` insert + `audit_trail` entry.
3. Node confidence change → `knowledge_versions` insert + confidence update.
4. Node pruning → status transition + `audit_trail` entry.
5. Edge weakening/breaking → `causal_links.status` change + `audit_trail`.

**Temporal Queries Supported:**
- *"What did the knowledge graph look like on [date]?"* → Queryable via point-in-time recovery or `knowledge_versions.created_at` bounds.
- *"What paths exist from Knowledge A to Knowledge B?"* → Recursive CTE on `causal_links` filtered by `status = 'active'`.

## 7. Event Storage Design

### 7.1 Event Schema Structure

All events written to `event_bus` conform to a standardized envelope:

**Required Envelope Fields:**

```sql
/* Conceptual event schema */
{
    -- Envelope metadata (always present)
    id                  : UUID           /* Primary key, server-generated */
    event_type          : TEXT           /* Domain-prefixed, e.g., 'discovery.validated' */
    aggregate_type      : TEXT           /* Entity type, e.g., 'knowledge_entry' */
    aggregate_id        : UUID           /* Entity instance ID */
    
    -- Payload (domain-specific)
    payload             : JSONB          /* Event-specific data, varies by event_type */
    
    -- Metadata (cross-cutting concerns)
    metadata            : JSONB          {
        correlation_id     : UUID    /* Request-scoped correlation */
        causation_id       : UUID    /* Preceding event causing this one (for chains) */
        trace_id           : UUID    /* Distributed trace root */
        source_service     : TEXT    /* Producer identity */
        schema_version     : TEXT    /* Contract version for payload shape */
    }
    
    -- Idempotency & ordering
    idempotency_key     : TEXT           /* Client-provided deduplication token */
    sequence_number     : BIGINT         /* Globally monotonic sequence */
    
    -- Timing
    occurred_at         : TIMESTAMPTZ    /* When the event happened in domain time */
    published_by        : TEXT           /* Producing service/engine identity */
    received_at         : TIMESTAMPTZ    /* When event bus received it */
}
```

**Event Type Naming Convention:**
- Format: `{domain}.{entity}.{action}`
- Examples: `discovery.signal.ingested`, `knowledge.entry.created`, `decision.approval.granted`, `governance.override.executed`

### 7.2 Correlation IDs

**Purpose:** Enable tracing end-to-end request flows spanning multiple services, events, and tables.

**Allocation:**
1. External requests generate fresh `correlation_id` (UUID v4).
2. Propagated through all downstream operations.
3. Stored in: `event_bus.metadata.correlation_id`, `audit_trail.correlation_id`, `system_logs.trace_id`, `error_log.request_context.correlation_id`.

**Query Capability:**
- Retrieve complete event sequence for given `correlation_id`.
- Link errors and exceptions to their originating request.
- Reconstruct causality chains for incident investigation.

### 7.3 Idempotency Handling

**Client-Side Idempotency Key:**

- Producers **MUST** include `idempotency_key` in every event submission.
- Uniqueness enforced via **UNIQUE constraint** on `event_bus(idempotency_key)`.
- On duplicate key detection:
  - Existing event returned (no new insertion).
  - No side effects triggered.
  - Standard HTTP-like 200 OK with original event body returned to subscriber query.

**Server-Safe Semantics:**
- Idempotency key scoping: Global (recommended) or per-event-type (if domain isolation required).
- Key lifetime: Effective indefinitely for `event_bus` (immutable log).
- Key format: Suggestion: `{producer_id}:{domain}:{operation}:{hash_of_payload}` for deterministic generation.

**Handling Non-Idempotent Sources:**
- For sources unable to provide client-side keys, event bus generates deterministic key from: `{source}:{event_type}:{aggregate_id}:{occurred_at}`.
- Collision resolution: Timestamp precision to microsecond + tiebreaker logic.

### 7.4 Dead Letter Queue Design

**Purpose:** Capture events that fail processing without losing them or blocking the main stream.

**Table: `event_dead_letter`**

**Fields:**
- `id` (UUID, primary key)
- `original_event_id` (UUID, references `event_bus`)
- `subscriber_id` (text, which consumer failed)
- `failure_reason` (text, error message)
- `failure_details` (JSONB, exception stack, retry count)
- `failure_timestamp` (timestamp with time zone)
- `retry_count` (integer, attempts made so far)
- `max_retries_exceeded` (boolean)
- `next_retry_after` (timestamp with time zone, exponential backoff schedule)
- `final_disposition` (enum: pending_retry, manually_resolved, permanently_failed, discarded_with_approval)
- `resolved_by` (text, nullable)
- `resolution_notes` (text, nullable)
- `resolved_at` (timestamp with time zone, nullable)
- `created_at` (timestamp with time zone)

**Dead Letter Processing Policy:**

| Retry Attempt | Backoff Delay | Action |
|---------------|---------------|--------|
| 1–3 | 30 seconds, 60 seconds, 120 seconds | Automatic retry by DLQ processor |
| 4–6 | 5 minutes, 15 minutes, 1 hour | Automatic retry with alert escalation |
| 7+ | 4 hours, then daily | Hold for manual investigation |

**Resolution Paths:**
1. **Retry Success**: Event processed successfully; DLQ record marked resolved.
2. **Manual Correction**: Engineer fixes underlying issue; triggers targeted re-processing.
3. **Discard With Approval**: Event acknowledged as unrecoverable and irrelevant; requires governance approval for discard.
4. **Permanent Failure**: Event confirmed as corrupt or invalid; archived separately.

### 7.5 Replay Strategy

**Purpose:** Ability to reconstruct state by replaying events from `event_bus`.

**Replay Modes:**

| Mode | Use Case | Implementation |
|------|----------|----------------|
| **Full Replay** | Disaster recovery, environment bootstrap | Replay entire event bus in `sequence_number` order |
| **Subset Replay** | Single entity state reconstruction | Filter events by `aggregate_type, aggregate_id`, replay in order |
| **Time Window Replay** | Point-in-time state inspection | Filter by `occurred_at` range, replay ordered |
| **Filtered Replay** | Re-process specific event types | Filter by `event_type` pattern match |

**Replay Guarantees:**
- At-least-once delivery during replay (subscribers handle deduplication).
- Deterministic ordering by `sequence_number` within single-partition events.
- Cross-partition ordering consistent up to clock-synchronization tolerance (configured <100ms).

**Replay Safety Constraints:**
- Replay environment isolated from production (separate database or schema).
- Requires explicit governance approval before production-state reconstruction.
- Cannot modify `event_bus` (append-only); replay projects to new state tables.
- `event_bus.sequence_number` serves as linearization authority.

### 7.6 Ordering Rules

**Global Ordering Model:**
- Monotonically increasing `sequence_number` assigned by database sequence.
- Single-writer assignment (database-generated via trigger or application-enforced).
- Gap detection: Monitoring alerts on any `sequence_number` gap > threshold (potential missed write).

**Per-Aggregate Ordering:**
- Within an entity's lifecycle, ordering guaranteed by `occurred_at` plus `sequence_number` tiebreaker.
- Subscribers can rely on: events for same `aggregate_id` arrive/process in creation order.

**Cross-Domain Ordering:**
- No hard guarantees across different `aggregate_type` groups within same millisecond.
- Use `causation_id` for explicit dependency chaining when ordering matters across domains.

### 7.7 At-Least-Once Guarantee Modeling

**Guarantee Level:** At-least-once delivery to subscribers.

**Implications for Subscribers:**
- Subscribers **MUST implement idempotent handlers**.
- Duplicate event reception is expected (especially after failures and replays).
- Idempotency checked via `event_bus.idempotency_key` or subscriber-maintained processed-set.

**Modeling in Database:**

```sql
/* Subscriber position tracking avoids re-delivery in normal flow,
   but duplicate delivery still possible around failure boundaries */

event_subscriptions.last_processed_sequence 
    -- Used by poller to avoid re-fetching completed events
    -- Subscriber still checks idempotency as safety net
```

**At-Least-Once Acceptance Criteria:**
- No event lost due to subscriber downtime or transient failure.
- Duplicates possible; bounded by replay window + failure scenario width.
- Exactly-once semantics achieved at subscriber layer via idempotency enforcement.

## 8. Audit & Compliance Design

### 8.1 Audit Trail Requirements

The `audit_trail` table constitutes the **primary compliance artifact** for all operations within AHOS. It is designed to satisfy regulatory frameworks applicable to cryptocurrency intelligence systems and financial data processing.

**Mandatory Capture Requirements:**

| Operation Category | Must Be Captured | Minimum Retention |
|-------------------|-------------------|-------------------|
| All writes (INSERT) | ✅ Yes | Per retention policy |
| All updates (UPDATE) | ✅ Yes (with old/new state) | Per retention policy |
| All soft deletes (STATUS change) | ✅ Yes | Per retention policy |
| Hard delete attempts | ✅ Yes (even if blocked) | Permanent |
| Read access to sensitive data | ✅ Yes (configurable logging level) | 12 months minimum |
| Authentication events (login/logout/session) | ✅ Yes | 12 months minimum |
| Authorization failures (denied access attempts) | ✅ Yes | 24 months |
| Configuration changes | ✅ Yes | 7 years |
| Governance actions (approvals/overrides) | ✅ Yes | 7 years |
| Export/bulk data retrieval | ✅ Yes | 7 years |
| System administration actions | ✅ Yes | 7 years |

**Non-Capturable Operations:**
- Internal database maintenance (VACUUM, reindexing) — logged in `system_logs`, not `audit_trail`.
- Replication stream activity — handled at infrastructure layer.
- Automated health checks — logged in `system_metrics`, not `audit_trail`.

### 8.2 Immutable Logs

**Immutability Architecture:**

`audit_trail` operates under **absolute immutability** constraints:

1. **INSERT-only Table**: No UPDATE or DELETE permissions granted to any role including superuser (enforced via trigger).
2. **Append-Only Access Pattern**: Application code exclusively uses INSERT.
3. **Physical Protection**: Database-level triggers block modification attempts:
   - On UPDATE: Raise exception "AUDIT_IMMUTABILITY_VIOLATION".
   - On DELETE: Raise exception "AUDIT_IMMUTABILITY_VIOLATION".
4. **Role-Based Enforcement**: Even database administrative roles cannot modify audit rows without explicit privilege escalation that itself generates audit records.

**Extension to Other Immutable Tables:**

| Table | Immutability Level | Rationale |
|-------|-------------------|-----------|
| `audit_trail` | Absolute (never updated/deleted) | Legal/compliance requirement |
| `event_bus` | Absolute (append-only) | Event sourcing correctness |
| `override_log` | Absolute (human accountability) | Governance integrity |
| `policy_versions` | Logical (versioned; individual rows immutable) | Policy lineage |
| `knowledge_versions` | Logical (versioned; individual rows immutable) | Knowledge provenance |

**Immutability Violation Detection:**
- `architecture_compliance` checks run periodically verifying no updates/deletes on protected tables.
- Any violation detected triggers **critical alert** to security team and governance stakeholders.
- Violation requires incident response per AHOS security protocol.

### 8.3 Governance Traceability

Each element stores references enabling forward and backward traversal:

**Cross-Reference Fields:**

### 8.7 Regulatory Retention Modeling

**Applicable Regulatory Contexts:**

AHOS data architecture anticipates retention requirements under potential regulatory frameworks applicable to cryptocurrency intelligence and financial technology systems.

**Retention Category Model:**

```sql
/* Conceptual retention category classification applied to all audited records */

retention_category enum (
    -- Operational (short)
    operational_logs       : 90 days hot, 1 year cold
    
    -- Transactional (medium)
    transaction_records    : 7 years (financial-grade)
```

**Retention Enforcement Implementation Approach:**

4. **Permanent Deletion**: After maximum retention period expires AND governance approval granted AND legal hold cleared: cryptographic erasure certification generated.

**Hold Mechanism:**

- `legal_hold` flag conceptually applicable (implementation may add column or external metadata service).
- Records under legal hold bypass ALL retention expiration until hold released.
- Hold placement/removal requires governance-level authorization and generates audit record.

### 9.2 Cold Storage Boundary (Conceptual)

**Boundary Definition:**

Cold storage boundary represents the transition point where data leaves the actively-queryable Supabase database and moves to external archival media optimized for infrequent access.

**Boundary Characteristics:**

| Dimension | Hot/Warm (Supabase) | Cold (External) |
|-----------|---------------------|-----------------|
| **Query Latency** | < 100ms typical | Minutes to hours (retrieval) |
| **Cost Profile** | Higher (SSD-backed) | ~1/10th cost (object/storage class) |
| **Availability** | High availability SLA | Best-effort retrieval |
| **Query Interface** | Full SQL | Search API / restoration required |
| **Indexing** | Full B-tree/JSONB/GiST indexes | Metadata index only; content opaque |

**Transition Process (Conceptual):**

1. **Identification**: Scheduler identifies records exceeding hot-retention threshold based on `created_at` + retention category rules.
2. **Preparation**: Selected records exported to standardized format (JSONL, Parquet, or PostgreSQL dump fragment).
3. **Validation**: Export checksum verified against database record hash.
4. **Transfer**: File uploaded to cold storage destination (S3 Glacier, Azure Archive, equivalent).
5. **Registration**: Metadata record created in Supabase indicating storage location, format, checksum, size.
6. **Confirmation**: Original records marked for deletion (soft-delete); physical purge occurs after verification period (configurable, default 30 days).
7. **Verification Spot-Check**: Random sampling of archived records retrieved and validated annually.

**Restoration Process:**

1. Restoration request submitted with justification (governance-approved).
2. Locate via cold-storage metadata registry in Supabase.
3. Initiate retrieval from cold storage (latency varies: minutes to hours depending on storage class).
4. Restore to temporary restoration environment (isolated schema/database).
5. Validate restored data checksums.
6. Make available to requesting party with audit trail entry.
7. Restoration expiry: Temporary restored data auto-purged after configurable access window (default: 72 hours).

## 10. Indexing & Performance Strategy

### 10.1 Primary Key Strategy

**Primary Key Type:** UUID (Universally Unique Identifier)

**UUID Version Selection:**

- **UUID v4** (random): Default for most tables.
  - Pros: Simple generation; no coordination required; sufficiently collision-resistant.
  - Cons: Index fragmentation over large tables; non-sequential page writes during INSERT-heavy workloads.

- **UUID v7** (time-sortable, recommended for high-volume tables):
  - Encodes timestamp in upper bits ensuring approximate chronological ordering.
  - Preferred for: `event_bus`, `signals`, `audit_trail`, `system_metrics`, `prediction_outcomes`.

**Recommendation:**
- Adopt **UUID v7** for all new table definitions where insertion volume exceeds 1000 rows/day.
- Existing v4 deployments maintained without forced migration unless performance issue identified.
- Application layer responsible for UUID generation (not database DEFAULT).

### 10.4 JSONB Usage Boundaries

**Approved JSONB Usage:**

| Field Category | JSONB Appropriate? | Rationale |

### 10.5 Query Optimization Principles

**AHOS-Wide Query Principles:**

1. **Targeted Fetches**: Always specify limiting conditions; avoid unconstrained `SELECT * FROM large_table`.
2. **Pagination Mandatory**: User-facing queries require `LIMIT`/`OFFSET` or cursor-based pagination for result sets > 100 rows.
3. **Covering Indexes Favorable**: For frequent read paths, include selected columns in index definition to enable index-only scans.
4. **Materialized Views for Aggregations**: Computationally expensive aggregations (calibration metrics, performance summaries) materialized and refreshed on schedule.
5. **EXPLAIN ANALYZE Culture**: Complex queries analyzed before production deployment; execution plans reviewed for sequential scans on large tables.
6. **Connection Pooling**: Supabase connection pooler configured appropriately for concurrent workload; application layer implements its own pooling where beneficial.
7. **Read Replicas Utilized**: Read-heavy workflows (reporting, analytics) directed to read replicas; single writer for mutations.
8. **N+1 Prevention**: GraphQL-like relationship loading patterns avoided; batch fetching with `IN (...)` or JOIN semantics enforced.

### 10.6 Partitioning Strategy

**Partitioning Applied To:**

High-volume, time-series tables benefit from **range partitioning on `created_at` / equivalent timestamp column**:

| Table | Partition Column | Partition Granularity | Rationale |
|-------|-----------------|----------------------|-----------|
| `event_bus` | `received_at` or `occurred_at` | Daily | Highest insert volume; strict ordering requirement |
| `signals` | `ingested_at` | Daily | High-frequency ingestion pipeline |
| `audit_trail` | `event_timestamp` | Weekly or Daily | Compliance-critical; large retention scope |
| `system_logs` | `logged_at` | Daily | Volume scales with log verbosity |
| `error_log` | `occurred_at` | Weekly | Lower volume than logs but still time-scoped queries |
| `system_metrics` | `recorded_at` | Daily | Obvious time-series nature |
| `prediction_outcomes` | `created_at` | Monthly | Moderate insert rate; long retention |
| `performance_records` | `recorded_at` | Monthly | Aggregated metric snapshots |

**Partition Management:**

1. **Auto-creation**: Partitions created ahead of time (lookahead: create next week/month partitions before they're needed).
2. **Drop/Detach Old Partitions**: Expired partitions detached (not immediately dropped) into archival staging before eventual cold storage transfer.
3. **Attach New Partitions**: Controlled via migration scripts; no ad-hoc partition creation.
4. **Default Partition**: No default/unbounded partition; ensures clean boundaries; misrouted data caught early.
5. **Index Inheritance**: Global indexes inherited to partitions; local indexes consistent across partitions.

**Partition Pruning Benefits:**

- Time-range queries automatically prune irrelevant partitions via constraint exclusion.
- Maintenance operations (VACUUM, REINDEX) scoped to single partitions.
- Archival operations operate on whole partition units simplifying extraction.

## 11. Row-Level Security (RLS) Hooks

### 11.1 Tenant Isolation (Future-Ready)

**Schema Preparation:**

All domain tables include optional `tenant_id` column (UUID, nullable):

```sql
/* Conceptual schema pattern applied uniformly: */
tenant_id UUID REFERENCES tenants(id) ON DELETE RESTRICT
         DEFAULT NULL  /* NULL represents default/single-tenant Phase 1 */
```

**Phase 1 Behavior (Single Tenant):**
- `tenant_id` consistently `NULL` or set to predefined default tenant UUID.
- RLS policies defined but disabled (`ENABLE ROW LEVEL SECURITY` not yet executed on tables).
- Code paths respect tenant_id presence/absence transparently.

**Phase N Behavior (Multi-Tenant Activation):**
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` executed under governance sign-off.
- Policies activate enforcing: `WHERE tenant_id = current_setting('app.current_tenant')::uuid`
- All queries implicitly filtered; explicit circumvention blocked.
- Migration path: backfill `tenant_id` across existing data; zero-downtime cutover.

**RLS Policy Definition (Conceptual for Future Enablement):**

```
POLICY tenant_isolation ON {table_name}
    FOR ALL TO authenticated_role
    USING (
        tenant_id IS NULL OR 
        tenant_id = current_setting('app.current_tenant')::uuid
    )
    WITH CHECK (same condition)
```

## 12. Backup & Restore Strategy

### 12.1 Continuous Backup Principle

AHOS data operates under a **continuous backup regime** ensuring point-in-time recoverability within configured recovery window objectives (RPO/RTO).

**Backup Architecture:**

| Component | Mechanism | Frequency | RPO Target |
|-----------|-----------|-----------|------------|
| **Base Backups** | PostgreSQL pg_basebackup or Supabase managed backup | Daily at low-activity window | 24 hours maximum data loss for base layer |
| **WAL Archiving** | Write-Ahead Log continuous archival to durable object storage | Continuous (every WAL segment) | Near-zero theoretical RPO; practical RPO ~ minutes |
| **Logical Export** | pg_dump / pg_dumpall in custom format | Weekly (supplemental) | Supplemental to base+WAL chain |
| **Cross-Region Replication** | Streaming replication to standby in alternate region | Synchronous or asynchronous per table criticality | RPO varies: sync = 0; async = configurable lag tolerance |

**Supabase-Specific Integration:**
- Leverage Supabase built-in automated backups (daily, 7-day retention standard).
- Configure extended retention where required by AHOS governance (critical tables → 30-day backup retention).
- Enable Point-in-Time Recovery (PITR) across all backed-up databases.

---

### 12.2 Point-in-Time Recovery

**Capability Scope:**

Any database state within the **PITR window** (minimum 30 days, recommended 90 days for production) is recoverable to an exact timestamp with transaction-level granularity.

**PITR Use Cases Supported by Data Architecture:**

| Scenario | PITR Application |
|----------|------------------|
| Accidental data corruption by application bug | Restore to pre-corruption timestamp; extract correct rows; replay subsequent valid transactions selectively |
| Malicious insider action detected late | Restore to pre-compromise timestamp; analyze delta to identify scope of damage |
| Failed migration requiring rollback | Restore pre-migration state; validate migration in isolated environment before re-attempt |
| Regulatory investigation requesting historical state as of specific date | Spin up read-only clone at specified timestamp for investigator access without affecting production |
| Knowledge graph analysis at past point in time | Clone database to temporal snapshot; query knowledge entries and causal links as they existed historically |

**Data Architecture Support for PITR:**

- All mutable operations generate `event_bus` entries enabling **logical reconstruction** even outside PITR window.
- Versioned entities (`knowledge_versions`, `hypothesis_versions`) enable **entity-level rollback** independent of full-database PITR.
- Immutable audit trail provides **forensic trail** even if full PITR not available for older periods.
- Soft-delete strategy ensures deleted records are restorable from PITR snapshot before physical purge windows expire.

**PITR Procedure (Conceptual):**

```
1. Identify target recovery timestamp (precise, include timezone).
2. Verify target timestamp falls within PITR retention window.
3. Initiate restore to new database instance (never overwrite production directly).
4. Validate restored instance: row counts, checksums on critical tables, sample data verification.
5. Document restoration in system_logs and architecture_compliance records.
6. If restoring to replace production: coordinate cutover during maintenance window with full validation cycle.
7. If restoring for read-only analysis: grant appropriate access; set expiry for temporary instance.
```

### 12.3 Snapshot Strategy

**Snapshot Types:**

| Snapshot Type | Frequency | Retention | Purpose |
|---------------|-----------|-----------|---------|
| **Production Snapshots** | Daily automatic + pre-maintenance manual | 7 days rolling (auto); 30 days for pre-maintenance | Rapid whole-database restore baseline |
| **Schema Snapshots** | Pre- and post-every migration execution | Permanent (version-controlled) | Migration rollback baseline; schema history |
| **Application-State Snapshots** | On-demand via operational procedure | 14 days default | Critical incident investigation starting point |
| **Cross-Environment Sync Snapshots** | Before promotion staging→production | Until promotion validated + 48 hours | Promotion safety net |

**Snapshot Governance:**

- All snapshots logged in `system_config` or dedicated `snapshot_registry` (conceptual) with:
  - Snapshot identifier
  - Timestamp
  - Trigger reason
  - Estimated size
  - Expiry date
  - Creator identity
- Automatic expiry enforced by scheduled job; extension requires explicit approval.
- Production snapshots encrypted at-rest using organization-standard key management.

### 12.4 Backup Verification Alignment

**Verification Requirements (aligned with Technical Architecture):**

| Verification Type | Method | Frequency | Success Criteria |
|-------------------|--------|-----------|------------------|
| **Existence Check** | Confirm backup file present in destination store | Every backup creation | File exists; size > 0 bytes expected range |
| **Integrity Check** | Run `pg_verifybackup` against base backup | Per base backup | Zero errors reported; all files pass checksum |
| **Restore Test (Smoke)** | Automated restore to scratch instance; start database; run basic connectivity queries | Weekly | Database starts; returns results for SELECT 1; critical tables return non-zero row counts |
| **Restore Test (Deep)** | Full restore to isolated environment; run validation suite against restored data | Monthly | All validation checks pass (row counts, foreign key integrity, index usability, sample data correctness) |
| **WAL Replay Test** | Recover to arbitrary recent time point using WAL archive chain | Weekly | Target timestamp achieved; transaction log consistent |
| **Cross-Region Sync Check** | Compare standby lag; verify replication status | Continuous monitoring via metrics | Replication lag < defined threshold; streaming active |

**Failure Response:**

- Any verification failure triggers **immediate alert** (P1 severity).
- Failed backup trigger immediate **re-run attempt**.
- Consecutive failures escalate to infrastructure team + governance notification.
- Deep test failure blocks pending maintenance window until remediation confirmed.

### 12.5 Restore Test Governance

**Scheduled Restore Testing Program:**

1. **Weekly**: Automated smoke-test restore (scratch database, basic queries). Results logged to `system_metrics`.
2. **Monthly**: Deep-validation restore including sample data spot-checks and consistency assertions. Results documented; any issues tracked as remediation items.
3. **Quarterly**: Full disaster-recovery drill simulating complete primary failure scenario. Includes failover execution, cutover procedures, and validation by human operators. Post-drill report filed with Architecture Review Layer.
4. **Annually**: Complete DR exercise involving external stakeholders (if applicable for regulatory requirements). Full documentation produced.

**Restore Test Documentation Requirements:**

Each restore test produces record containing:

- Test type and scope
- Target restore point selected
- Duration of restore operation
- Validation checks executed with pass/fail status
- Deviations observed
- Personnel involved
- Lessons learned
- Sign-off approving return-to-normal

### 12.6 Disaster Recovery Compatibility

**DR Tier Classification:**

AHOS data architecture supports multiple DR tiers based on RPO/RTO requirements:

| DR Tier | RPO | RTO | Data Architecture Support | Applicable To |
|---------|-----|-----|--------------------------|---------------|
| **Tier 1 — Hot Standby** | < 5 min | < 15 min | Synchronous replication; instant failover | Real-time trading decisions, live market data pipelines |
| **Tier 2 — Warm Standby** | < 1 hour | < 4 hours | Asynchronous replication; planned failover | Analytics reporting, batch processing, non-time-critical engines |
| **Tier 3 — Cold Recovery** | < 24 hours | < 24 hours | Base backup + WAL archive PITR | Historical analysis environments, development clones, compliance investigations |

**Data Architecture Features Enabling Each Tier:**

**Tier 1 Enablers:**
- Synchronous replication confirmed for `event_bus`, `actions`, `decisions` tables.
- Idempotency keys prevent duplicate processing during failover scenarios.
- Sequence numbers provide ordering guarantee even with replication switchover.

**Tier 2 Enablers:**
- All data eventually consistent after async catch-up.
- Versioned entities tolerate brief inconsistency windows; current pointers resolve once caught up.
- Audit trail preserved through both primary and standby with eventual reconciliation.

**Tier 3 Enablers:**
- PITR capable of recovering to any point in retention window.
- Event sourcing pattern enables logical reconstruction beyond binary recovery.
- Knowledge versioning enables entity-level recovery independent of full DB restore.

**Recovery Priority Ordering (Precedence for restore sequence):**

1. **Governance tables** (`audit_trail`, `override_log`, `approvals`) — non-negotiable priority; must never lose governance records.
2. **Event stream** (`event_bus`) — reconstruction source for everything else.
3. **Knowledge core** (`knowledge_entries`, `knowledge_versions`) — highest business value asset.
4. **Operational state** (`discoveries`, `decisions`, `actions`, `hypotheses`) — current system state.
5. **Observability** (`system_logs`, `error_log`, `system_metrics`) — diagnostic capability.
6. **Infrastructure config** (`system_config`, `contract_registry`) — recoverable but may have cached alternatives.

## 13. Migration & Evolution Strategy

### 13.1 Schema Migration Process

**Migration Lifecycle Stages:**

```
[Design] → [Review] → [Staging] → [Production Planning] → [Execution] → [Verification] → [Documentation]
```

**Stage Details:**

**1. Design**
- Engineer drafts migration script following naming convention:
  - `{timestamp}_{brief_description}.sql`
  - Example: `20240615143000_add_confidence_decay_to_knowledge.sql`
- Script includes header comment block:
  - Purpose description
  - Affected tables/columns
  - ADR reference(s) if architectural decision driven
  - Approval references if breaking change
  - Rollback script path/inline content
  - Estimated runtime and lock impact assessment
- Schema changes modeled against `contract_registry` for forward compatibility validation.

**2. Review**
- Code review by peer engineer.
- Architecture Review for changes crossing domain boundaries or introducing breaking changes.
- Security review for changes affecting RLS policies, permissions, or sensitive columns.
- Performance review for index additions/removals or large-table alterations.
- Approval recorded (linked to `approvals` if governance-gated).

**3. Staging Execution**
- Migration applied to staging environment (production data copy where possible or synthetic data).
- Full regression test suite executed post-migration.
- Rollback tested on staging (reverse migration verified functional).
- Performance benchmarks compared pre/post migration.

**4. Production Planning**
- Maintenance window identified (or zero-downtime strategy confirmed).
- Backout plan documented with clear rollback triggers.
- Communication sent to dependent teams/systems.
- Monitoring dashboards prepared for migration-specific alerts.
- On-call engineer designated for migration window.

**5. Execution**
- Migration deployed via controlled deployment pipeline.
- Transaction boundaries respected (single logical migration per script).
- Lock impact monitored via `pg_stat_activity` / Supabase monitoring.
- If multi-statement migration: wrapped appropriately with error handling.

**6. Verification**
- Post-deployment checks execute automatically:
  - Table structure matches expectation (column existence, types, constraints).
  - Row count sanity checks (no accidental data loss/gain).
  - Index validity confirmed (usable, not INVALID).
  - Foreign key constraints intact.
  - Sample query response times acceptable.
- Application health checks pass against migrated schema.
- Error rate within normal bounds for initial observation period (30-minute minimum).

**7. Documentation**
- Migration marked complete in tracking system.
- ADR updated if structural change reflects or alters architectural decision.
- `architecture_compliance` record created capturing change metadata.
- Changelog updated for release notes.

### 13.2 Backward Compatibility

**Backward Compatibility Principles:**

1. **Column Addition Always Safe**: New nullable columns with defaults cause no breakage.
2. **Column Removal Never Safe Without Deprecation**: Existing consumers require migration path.
3. **Type Widening Generally Safe**: E.g., VARCHAR(50) → VARCHAR(255), INT → BIGINT.
4. **Type Narrowing Always Breaking**: Requires deprecation + migration coordination.
5. **Constraint Addition Potentially Breaking**: NOT NULL constraints on existing nullable columns require backfill strategy first.
6. **Enum Value Addition Safe**: Enum value removal requires deprecation period.

**Deprecation Protocol for Breaking Changes:**

When a breaking schema change is necessary:

| Phase | Duration | Actions |
|-------|----------|---------|
| **Announcement** | Day 0 | Document impending change; notify all consumers; tag affected contracts in `contract_registry` with `status = 'deprecation_announced'` |
| **Compatibility Window** | Minimum 30 days (standard); 90 days (external/integration dependencies) | Consumers adapt to upcoming shape; dual-read/write support if needed |
| **Warning Period** | Final 7 days of compatibility window | Log deprecation warnings on every access to soon-to-be-changed elements; alert on high usage |
| **Cutover** | During maintenance window | Execute breaking migration; remove deprecated code paths; update contract registry to `status = 'active'` for new shape |
| **Observation** | 72 hours minimum post-cutover | Monitor for unexpected errors; rapid rollback available if issue severity warrants |

---

### 13.3 Rolling Migration Approach

**Database Migration Compatibility with Application Deployment:**

AHOS supports **rolling deployments** where application instances are upgraded incrementally while remaining available. The database layer must tolerate mixed-version application instances briefly coexisting.

**Schema Strategies Supporting Rolling Deployments:**

| Change Type | Rolling-Compatible? | Technique |
|-------------|-------------------|-----------|
| Add column | ✅ Yes | Column added before deploy; apps ignore until activated; safe because NULL default or benign default value doesn't affect old code |
| Add table | ✅ Yes | Table exists unused; only new code references it |
| Add index | ⚠️ With caution | CONCURRENTLY index building avoids table locks but requires careful timing |
| Modify column default | ⚠️ With caution | Old apps may write old defaults; handle in application logic or post-migration backfill |
| Rename column | ❌ No | Breaks all existing reads/writes; use add-new-drop-old deprecation flow |
| Change column type | ❌ No (usually) | Requires full column rewrite; schedule maintenance or use expand-contract pattern |
| Remove column | ❌ No (until all consumers updated) | Deprecate first; only drop after confirming zero references |
| Add constraint | ⚠️ Varies | NOT NULL requires data validation first; CHECK constraints may reject existing data |

**Expand-Contract Pattern (for otherwise-breaking column changes):**

1. **Expand**: Add new column alongside old column (e.g., `amount_cents` alongside `amount_decimal`).
2. **Migrate**: Backfill new column from old column values.
3. **Redirect**: Update all writers to populate new column (dual-write transition period).
4. **Verify**: Confirm new column consistently populated; readers switch to new column.
5. **Contract**: Remove old column (following deprecation protocol above).

This pattern enables gradual migration without any single breaking moment requiring downtime.

### 13.4 Version Tagging

Every schema migration carries semantic version linkage:

**Version Tag Format:**

```sql
/* 
 * Migration: 20240615143000_add_knowledge_branching_support
 * AHOS Version: v1.2.0
 * Domain: Knowledge Architecture
 * ADR Reference: ADR-0042 (Knowledge Branching and Lineage Tracking)
 * Breaking: No
 * Previous Version Required: v1.1.0+
 */
```

**Tag Relationships:**

- **Single Source of Truth**: Database schema version derives from the highest migration applied.
- **Application Compatibility Matrix**: Each application/engine version declares compatible schema version ranges.
- **Deployment Gate**: System refuses startup if schema version falls outside declared compatibility range.
- **Audit Trail**: Schema version recorded in `system_config` key `schema.current_version` after each successful migration.

### 13.5 Governance Approval Requirement for Breaking Changes

**Breaking Change Definition (Triggers Mandatory Governance Review):**

A schema change qualifies as "breaking" if ANY of the following conditions hold:

| Condition | Examples |
|-----------|----------|
| Removes or renames any public-facing element (table, column, function, view, enum value) | Drop column, rename table, remove enum variant |
| Changes data type of any column in a way that is lossy or incompatible | INT → TEXT is fine; TIMESTAMP without TZ → TIMESTAMP with TZ may be problematic depending on app handling |
| Adds or modifies constraints that could reject existing valid data | Adding NOT NULL to nullable column with existing NULLs; adding CHECK that existing rows violate |
| Modifies behavior of any function or stored procedure used by more than one consumer | Changing output format, parameter requirements, error behavior |
| Alters partitioning scheme of a high-volume table | May invalidate existing queries expecting old partition layout |
| Changes encryption, encoding, or collation settings for existing columns | Could affect comparison semantics |
| Impacts RLS policy definitions in a way that could deny previously-granted access | Tightening security is good but may break legitimate workflows unexpectedly |

**Governance Process for Breaking Changes:**

1. **Breakage Assessment Form**: Engineer completes template documenting nature of breakage, affected consumers, risk assessment, mitigation plan.
2. **Consumer Impact Analysis**: Identify all systems/codebases querying affected elements. Query `pg_stat_user_tables`, review application code search.
3. **Architecture Review Submission**: Submit to Architecture Review Layer with ADR draft proposing change rationale.
4. **Approval Record Creation**: `approvals` entry created with `approval_type = 'breaking_schema_change'`.
5. **Approval Workflow Execution**: Assigned approvers (minimum: one architect, one representative from most-affected consuming domain) review and approve/reject.
6. **Approval Recorded**: Approved migration tagged with `approval_record_id` in comments.
7. **Proceed Only After Approval**: CI/CD pipeline gates on presence of approved `approval_id`; breaks build without it.

## 14. Validation Criteria

### 14.1 Architectural Compliance Checklist

**Pre-Migration and Periodic Compliance Checks:**

Every schema modification and weekly automated scans verify these criteria:

| # | Criterion | Validation Method | Failure Action |
|---|-----------|-------------------|----------------|
| C1 | All tables have `created_at` and `updated_at` columns with proper types (TIMESTAMPTZ) | Query information_schema.columns for all user tables | Block migration; add missing columns |
| C2 | All tables use UUID primary keys (except junction/association tables which may use composite) | Query table definitions for PK type | Flag warning (junction tables exemptible) |
| C3 | All domain tables include optional `tenant_id` column (nullable, UUID type) | Scan for tenant_id absence on tables in domain list | Block migration; add column |
| C4 | Immutable tables have NO UPDATE/DELETE grants to any role except trigger context | Query privilege grants; validate trigger guards exist | Critical failure; immediate remediation |
| C5 | Versioned entity tables have corresponding `{table}_versions` table with correct FK relationship | Cross-reference domain definition registry | Block migration; create missing versions table |
| C6 | All foreign key relationships declare ON DELETE behavior explicitly (not defaulted) | Query foreign_keys for ON DELETE clause | Warning; enforce explicit declaration |
| C7 | Indexes exist for all required fields per Section 10 specifications | Compare actual indexes against specification catalog | Create missing indexes |
| C8 | No SELECT * exists in any materialized view or stored procedure definition (explicit column lists) | Search pg_views and pg_proc definitions | Refactor to explicit columns |
| C9 | All JSONB columns accessing frequently-filtered fields have GIN indexes where appropriate | Cross-reference JSONB columns vs GIN index inventory | Evaluate and add if warranted |
| C10 | Partitioned tables have partitioning configured according to Section 10.6 specifications | Verify partition schemes match defined strategy | Reconfigure partitioning |
| C11 | RLS-compatible design patterns followed even if RLS not yet enabled (tenant_id presence, no bypass patterns) | Static analysis of schema vs RLS-ready checklist | Note for future enablement readiness |
| C12 | Contract registry entry exists or is not-required-flagged for each public table | Cross-reference tables vs contract_registry | Register missing contracts |

### 14.2 Drift Prevention

**Drift Detection Mechanisms:**

| Drift Type | Detection Method | Prevention Strategy |
|------------|-----------------|---------------------|
| **Schema Drift** (unauthorized schema modifications outside migrations) | Hash of schema exported daily; compare to last known-good hash; deviation triggers alert | Only migration scripts modify schema; direct DDL blocked in production via role restrictions |
| **Data Drift** (data violating model constraints introduced by buggy writes) | Constraint enforcement at DB level; periodic anomaly detection queries looking for nullity violations, orphaned FK references, status enum violations | Application-level validation plus DB-level constraints as defense-in-depth |
| **Permission Drift** (grant creep, unauthorized role expansion) | Periodic permission dump compared to baseline; any new GRANT flagged | Role-based access control centralized; ad-hoc grants prohibited |
| **Index Drift** (missing or extraneous indexes relative to spec) | Weekly reconciliation of actual indexes vs specification document | Index additions/removals via migration only |
| **Config Drift** (system_config values deviating from approved baselines) | Config diff audit comparing current values to last-approved snapshot | Configuration changes go through approval workflow |
| **Compliance Drift** (tables falling out of alignment with ADR-defined structures) | Architecture compliance scanner runs queries verifying ADR-derived invariants | Architecture Reviews approve structural changes |

**Drift Response Protocol:**

1. **Detection Alert**: Automated alert fires to on-call engineering channel.
2. **Assessment**: Triage determines drift category (benign, concerning, critical).
3. **Benign**: Documented as accepted variance; added to exclusion list for future scans.
4. **Concerning**: Remedy plan created; scheduled fix within sprint cycle.
5. **Critical**: Immediate incident response; potential rollback if recent change induced drift; involve Architecture Review Layer.

### 14.3 Determinism Validation

**Deterministic Execution Guarantees Verified Through:**

| Aspect | Validation Approach |
|--------|-------------------|
| **Event Ordering Determinism** | Event bus sequence numbers are monotonic and gap-free (within bounded tolerance); replay yields identical state to original execution order |
| **Idempotency Determinism** | Duplicate idempotency keys produce idempotent results regardless of retry count or ordering of interleaved concurrent requests |
| **Confidence Calculation Determinism** | Decay formula applied to same inputs always yields same output; scheduler recalculations converge identically given identical input snapshots |
| **State Transition Determinism** | State machine transitions are deterministic functions of current state + event payload; no hidden variables, no randomness in state derivation |
| **Validation Score**: Given identical input data and parameters, scoring algorithms produce identical numeric outcomes (floating-point determinism managed via deterministic rounding rules) |
| **Query Result Stability** | Same query on unchanged data returns identical result sets; no non-deterministic ORDER BY clauses (always specify explicit sort keys); LIMIT/OFFSET pagination replaced with cursor-based for stability where order matters deterministically |

**Testing Regime for Determinism:**

- **Property-Based Testing**: Generate random but controlled inputs; assert that repeated execution with identical inputs produces identical outputs.
- **Snapshot-Compare Tests**: Capture database state before operation; execute operation; capture after state; compare against known-good expected delta.
- **Race Condition Simulation**: Concurrent client simulation executing overlapping writes protected by idempotency keys and serialization guarantees; verify no anomalies.
- **Time-Freezing Tests**: Control simulated clock during confidence decay calculations; assert predictable values.

### 14.5 Replayability

**Event Stream Replayability Validation:**

| Replay Capability | Validation Criterion |
|------------------|---------------------|
| **Complete State Reconstruction** | Running entire event bus from empty database through current sequence number reproduces current state exactly (allowing for floating-point precision tolerance on computed fields like current_confidence) |
| **Subset Entity Reconstruction** | Filtering events for specific aggregate_type/aggregate_id and replaying yields identical entity state to production for that entity |
| **Point-in-Time Consistency** | Replaying events up to timestamp T produces state exactly matching what existed at time T (verified against snapshots taken near time T for sampling) |
| **Deterministic Side Effects** | Events that trigger side effects (notifications, external calls) produce consistent results on replay (side-effect handlers themselves must be idempotent; database provides the deterministic foundation) |
| **Idempotent Re-Replay** | Replaying already-replayed events does not corrupt state (idempotency keys protect) |
| **Speed** | Replay throughput supports reconstructing state within SLA targets for DR scenarios (benchmarked; documented as performance requirement) |

**Replay Validation Testing:**

- **Weekly Smoke Test**: Take production database; spin up clone; reset to empty event-consuming tables; replay event bus subset (last 24 hours); compare resulting table states byte-for-byte (ignoring immutable metadata timestamps where slight clock skew permissible).
- **Monthly Deep Test**: Full event bus replay from earliest retained event to current; measure duration; compare end-state hashes against production golden hash.
- **Per-Migration Validation**: After schema migration, verify that preceding events can still replay through new schema without error (forward compatibility of event payloads with evolved schema).

### 14.6 Observability Completeness

**Observability Coverage Validation:**

All observable aspects of data layer are instrumented and queryable:

| Observability Dimension | Completeness Criterion |
|------------------------|----------------------|
| **Write Path Instrumentation** | Every INSERT generates audit_trail entry and/or event_bus entry; no silent writes |
| **Read Path Logging** | Sensitive data accesses captured per Section 8 configuration; read volumes reflected in connection pooling metrics |
| **Error Capture** | Every exception/failure captured in error_log with sufficient context for diagnosis; no swallowed exceptions at data layer |
| **Latency Visibility** | Database query latency measurable per operation type via system_logs correlation or direct metric emission |
| **Volume Metrics** | Rows written/read per table per interval available via system_metrics aggregation |
| **Schema Change Auditing** | Every DDL operation creates audit_trail entry (via trigger or tooling); schema versions trackable over time |
| **Capacity Indicators** | Table sizes, index sizes, bloat indicators available via system_metrics or periodic informational queries |
| **Connection Health** | Pool saturation, connection wait times, idle connections observable |
| **Replication Lag** | If replication configured, lag between primary and replicas continuously visible |
| **Lock Contention** | Long-running locks detectable via monitoring; blocking queries identifiable |

**Observability Gap Scans:**

Automated scan identifies:
- Tables missing from `system_metrics` coverage for INSERT volume.
- Operations lacking `system_logs` coverage.
- Tables without `error_log` integration points for their domain's error scenarios.
- Missing health-check endpoints touching database liveliness.
- Gaps addressed systematically; each gap logged as technical debt item with remediation timeline.
