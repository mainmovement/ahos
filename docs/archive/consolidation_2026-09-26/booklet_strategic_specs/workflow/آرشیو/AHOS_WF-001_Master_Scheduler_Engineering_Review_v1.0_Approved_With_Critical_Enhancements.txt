# WF-001 Master Scheduler — Complete Engineering Review

## Review Classification: **APPROVED WITH CRITICAL ENHANCEMENTS**

## Overall Assessment

The WF-001 specification demonstrates **strong architectural foundations** and proper adherence to AHOS principles. The workflow correctly identifies its responsibility as pure orchestration without business logic contamination.

However, several **critical engineering gaps** must be addressed before implementation to ensure production readiness, fault tolerance, and operational reliability on a single-laptop deployment.

```
- Configuration reload
- Emergency stop signal
- Health check requests
```

## ❌ Section 7: Execution Rules — **CRITICAL MISSING LOGIC**

**Issues Identified:**

1. **No definition of "workflow already running"**
   - How is execution state determined?
   - Where is state stored?
   - What happens if state becomes inconsistent?

2. **No execution timeout enforcement**
   - Workflows may hang indefinitely
   - System resources may be exhausted
   - No recovery mechanism defined

3. **No priority definition**
   - What determines priority?
   - How are priorities enforced?
   - Can high-priority workflows preempt low-priority ones?

4. **Dependency mechanism undefined**
   - How are dependencies declared?
   - Where are dependency graphs stored?
   - What happens if a dependency fails?

**Why These Matter:**

On a single laptop:
- Stuck workflows consume RAM/CPU indefinitely
- Database locks may deadlock the system
- Cascading failures cannot be prevented without proper dependency handling

**Recommended Replacement:**

```
## 7. Execution Rules

The scheduler shall enforce the following rules:

### 7.1 Execution State Management

**State Storage:**
- Current execution state stored in `workflow_queue` table
- States: `idle`, `queued`, `running`, `completed`, `failed`, `timeout`
- State transitions logged with timestamps

**Duplicate Prevention:**
- Before triggering, check `workflow_queue.status` for workflow_id
- If status = `running`, reject new execution
- If status = `queued`, wait until completion
- If status = `timeout` or `failed`, apply retry policy

### 7.2 Timeout Enforcement

**Default Timeout:**
- Per-workflow configurable timeout (default: 15 minutes)
- Stored in `configuration` table
- Enforced via scheduled timeout check (every 60 seconds)

**Timeout Handling:**
- Mark workflow as `timeout` in database
- Log timeout event
- Attempt graceful termination (future)
- Release execution lock
- Notify operator if workflow is critical

### 7.3 Priority Management

**Priority Levels:**
- `critical` (security checks, portfolio updates)
- `high` (opportunity discovery, market intelligence)
- `normal` (reporting, learning)
- `low` (archival, cleanup)

**Priority Enforcement:**
- Higher priority workflows execute first when queue has capacity
- Running workflows are NOT preempted
- Priority stored in `workflow_queue.priority`

### 7.4 Dependency Handling

**Dependency Declaration:**
- Dependencies stored in `workflow_dependencies` table
- Schema: `workflow_id, depends_on_workflow_id, dependency_type`
- Dependency types: `must_complete_successfully`, `must_complete`, `must_not_be_running`

**Dependency Resolution:**
- Before execution, query all dependencies
- Check completion status of required workflows
- If dependencies unsatisfied, mark as `waiting`
- Retry dependency check every 60 seconds
- Maximum wait time: configurable (default: 30 minutes)

**Dependency Failure:**
- If required workflow fails, dependent workflow transitions to `blocked`
- Operator notification required
- Manual approval required to override dependency

### 7.5 Infinite Loop Prevention

**Maximum Retry Limit:**
- Per-workflow configurable (default: 3)
- Tracked in `workflow_queue.retry_count`

**Backoff Strategy:**
- First retry: immediate
- Second retry: 60 seconds
- Third retry: 300 seconds
- After max retries: mark as `permanently_failed`
- Operator approval required to reset
```

## ⚠️ Section 8: Error Handling — **INCOMPLETE**

**Issue Identified:**

Missing **specific operator notification thresholds** and **automatic degradation strategy**.

**Why This Matters:**

On laptop deployment:
- Operator may not be monitoring Telegram 24/7
- System must continue operating through non-critical failures
- Critical vs non-critical failures must be distinguished

**Recommended Enhancement:**

Add after current content:

```
### 8.1 Notification Thresholds

**Critical Failures (Immediate Telegram Alert):**
- Database connection lost
- Master Scheduler crash
- All workflows failing simultaneously
- Security workflow failure
- Portfolio workflow failure

**Non-Critical Failures (Batched Report):**
- Single workflow retry
- Low-priority workflow timeout
- Temporary API unavailability
- Learning workflow failures

### 8.2 Degraded Mode Operation

If database is temporarily unavailable:
- Continue executing critical workflows if possible
- Queue non-critical workflows for later execution
- Log to local file system as fallback
- Attempt database reconnection every 60 seconds
- Alert operator after 5 minutes of database unavailability
```

## ⚠️ Section 9: Retry Policy — **NEEDS PRECISION**

**Issue Identified:**

Retry policy does not distinguish between **transient failures** (network timeout) and **permanent failures** (invalid configuration).

**Why This Matters:**

Retrying a misconfigured workflow wastes resources and delays operator awareness of the problem.

**Recommended Enhancement:**

```
## 9. Retry Policy

### 9.1 Failure Classification

**Transient Failures (Retry Automatically):**
- Network timeout
- API rate limit
- Temporary database lock
- External service unavailable

**Permanent Failures (No Retry, Immediate Notification):**
- Invalid workflow configuration
- Missing database table
- Authentication failure
- Code error (null reference, syntax error)

### 9.2 Retry Strategy

**For Transient Failures:**
- Retry Count: 3
- Retry Delays: 0s, 60s, 300s (exponential backoff)
- After 3 failures: mark as `failed`, notify operator

**For Permanent Failures:**
- No retry
- Immediate operator notification
- Workflow disabled until manually fixed

### 9.3 Retry Reset

- Successful execution resets retry counter
- Retry history preserved in logs
```

# CRITICAL MISSING SECTIONS

---

## ❌ MISSING: Initial Execution Sequence

**Problem:**

The specification does not define **what happens when AHOS starts for the first time** or **restarts after a crash**.

**Required New Section:**

```
## 21. System Initialization

When Master Scheduler starts:

1. Verify database connectivity
2. Verify all required tables exist
3. Check for workflows in `running` state
   - If found, investigate crash
   - Mark as `crashed`
   - Log event
   - Notify operator
4. Load configuration from database
5. Initialize workflow queue
6. Resume `queued` workflows
7. Begin normal scheduling
8. Send "System Ready" notification to operator

**Cold Start:**
- First execution after fresh installation
- Initialize default configuration
- Populate workflow definitions
- Execute health check workflow
- Await operator confirmation before full operation
```

---

## ❌ MISSING: Graceful Shutdown

**Problem:**

The specification does not define **how the system stops safely**.

**Required New Section:**

```
## 22. Graceful Shutdown

When shutdown signal received (SIGTERM, Docker stop):

1. Stop accepting new workflow triggers
2. Wait for running workflows to complete (max 5 minutes)
3. Mark incomplete workflows as `interrupted`
4. Flush all logs to database
5. Close database connections gracefully
6. Send "System Shutdown" notification
7. Exit with code 0

**Forced Shutdown (SIGKILL):**
- Recovery handled during next startup (Section 21)
```

---

## ❌ MISSING: Manual Intervention Protocol

**Problem:**

The specification does not define **how the operator manually controls workflows**.

**Required New Section:**

```
## 23. Manual Control Interface

The operator may issue commands via Telegram:

**Commands:**
- `/start_workflow <workflow_id>` — Manual execution
- `/stop_workflow <workflow_id>` — Graceful stop
- `/restart_workflow <workflow_id>` — Stop + Start
- `/reset_workflow <workflow_id>` — Clear failed state
- `/pause_scheduler` — Stop all new executions
- `/resume_scheduler` — Resume normal operation
- `/scheduler_status` — Display current state

All manual commands:
- Logged with operator ID
- Require confirmation for critical workflows
- Override normal priority rules
```
