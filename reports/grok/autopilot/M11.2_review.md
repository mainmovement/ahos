## آرش (architecture) — the defect that is actually live

`launcher/ahos.ps1` is saved as **UTF-8 without a BOM**. Windows PowerShell 5.1
has no encoding sniffing for BOM-less files: it decodes them with the system
ANSI codepage (cp1252 on this host). The file carries two Persian literals —
the fatal no-venv message and the `-Console` exit prompt — so on the owner's
machine those bytes are reinterpreted and the owner reads mojibake instead of a
message. This is the same failure class `test_install_windows_is_ascii_only`
was written for, applied to the one file the spec scopes.

**Proven on this host, not argued.** The committed file was copied into a
venv-less temp directory and executed through the real
`C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` (the exact binary
`AHOS.lnk` targets — verified via the `WScript.Shell` COM object:
`-NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File
"G:\robat\ahos\launcher\ahos.ps1" -Action start`, `WindowStyle=7`):

```
exit=3
b'\n\xd9\x85\xd8\xad\xdb\x8c\xd8\xb7 \xd9\xbe\xd8\xa7\xdb\x8c\xd8\xaa\xd9\x88\xd9\x86 ...'
   decoded as UTF-8 -> '\nÙ…Ø­ÛŒØ· Ù¾Ø§ÛŒØªÙˆÙ† Ù¾ÛŒØ¯Ø§ Ù†Ø´Ø¯. ÛŒÚ© Ø¨Ø§Ø± ...'
```

That is double-encoded garbage: `محیط پایتون پیدا نشد` never reaches the
owner. The control flow is unaffected (exit 3, no hang), so the launcher still
*works* — it just cannot say what is wrong, on the one path where the owner
most needs it to.

**Fix (scope: `launcher/ahos.ps1` only).** Save the file as UTF-8 *with* a BOM.
WinPS 5.1 honours the BOM and decodes correctly; PowerShell 7 is unaffected.
Re-run of the same experiment after prepending `EF BB BF`:

```
exit=3
'\nمحیط پایتون پیدا نشد. یک بار install_windows.ps1 را اجرا کنید.\n\n'
```

Exactly the intended string. This is a one-content-byte-order change: no logic
in the script is touched, because no logic is broken.

**Why not move the Persian out to `launcher/persian.py` instead?** That would
be the other honest fix, but the fatal no-venv branch is precisely the branch
where Python cannot be started, so the shell must own at least one message.
The BOM keeps that message correct at zero structural change.

**Latent part of the spec, structurally impossible today.** The spec's second
half (stderr lines becoming terminating `NativeCommandError` under
`$ErrorActionPreference = 'Stop'`) requires `2>&1` redirection into the
PowerShell error stream. The committed hidden path has *no* redirection at all
— python writes the log itself — so the trap has no surface to fire on. I am
not adding a "fix" for a shape that no longer exists; I am adding a static test
that makes the shape impossible to reintroduce (no python call inside a
`catch`, no PowerShell pipe wrapping the python call).

Authority surface: `launcher/ahos.ps1` + `tests/test_phase18_launchers.py`
only. No Lane A, no `architecture/`, no gate, no policy, no freeze file.

## پروانه (prompt / spec clarity)

Two of the spec's three named static tests are literal and I implement them
verbatim. The third needs a correction, and I am stating it rather than
silently substituting:

> "hidden path writes via `[IO.File]::AppendAllText` or `Out-File -Encoding utf8`"

That names the **R5** design, which R6 superseded and which itself wedged the
shell (a PowerShell pipe ends when the *write* end closes, and the launcher's
detached children inherit that handle — eight zombie `powershell.exe` processes
held the module lock on this host before R6). Pinning `Out-File` into a test
would re-forbid the working design. The *intent* the sentence serves is: *the
hidden path must actually produce a UTF-8 log, with each line written once, and
the exit code must still be python's.* I pin that intent against the mechanism
that is really in the repo — the `AHOS_LAUNCHER_LOG` env contract and the
Python-side `_Tee` — and the docstring records the supersession so a reviewer
reading the spec later is not confused by the mismatch.

Acceptance's owner-run receipt is deliverable on this session: this is a
Windows host with the real `.venv`, the real PS 5.1 binary and the real
`AHOS.lnk`. That is stronger than the box's read-only review.

## Sign-offs

### رضا (red team) — tried to break it

**Attack 1 — do the new guards actually fire?** Six mutations were injected
into a temp copy of `launcher/ahos.ps1` and each was run against its guard
(harness: `C:\Users\Sniper\AppData\Local\Temp\m112_mut.py`, not committed — it
is a throwaway attacker tool, not a repo test):

| Mutation | Guard | Result |
|---|---|---|
| BOM stripped | `test_ahos_ps1_is_utf8_with_a_bom` | **fired** |
| `& $Python @PyArgs \| Tee-Object -Encoding utf8 log.txt` reintroduced | `test_no_tee_object_encoding_in_the_launcher` | **fired** |
| `& $Python @PyArgs` placed inside the first `catch` | `test_the_python_action_is_never_re_run_from_a_catch` | **fired** |
| `\| Out-File -Encoding utf8 launcher.log` wrapped around python | `test_no_powershell_pipe_wraps_the_python_call` | **fired** |
| `$env:AHOS_LAUNCHER_LOG` renamed to `..._DISABLED` | `test_hidden_path_names_the_log_python_writes` | **fired** |
| `exit $rc` replaced with `exit 0` | `test_pythons_exit_code_reaches_the_shell_exit` | **fired** |

All six mutations were caught; the unmutated committed file passes all five.
Guards that pass on broken input were not accepted.

**Attack 2 — the red team found a real bug in my own work.** The first version
of `_ps_catch_bodies` started brace depth at `0` and yielded when depth returned
to `0`. That stops at the *first* close brace inside the handler, so a
`catch { try { ... } ... }` was truncated and a python call after the inner
`try` was invisible to the guard — mutation 3 passed when it should have failed.
Fixed to start depth at `1` (matching the working brace-matcher already in
`TestNoVisibleConsole`), then re-verified. The bug was in the test helper, not
in `ahos.ps1`, but a blind guard is worse than no guard, so it is recorded here
rather than quietly patched.

**Attack 3 — does the BOM break anything else?**
- `git diff` sees a one-line text change (the BOM joins the first line), not a
  binary rewrite. `.gitattributes` pins `*.ps1 text eol=crlf`, so CRLF
  survives; verified `0` bare LF after the change.
- The AST parse of the committed file under the real 5.1 binary succeeds
  (`PARSE_OK`), and the file runs to its intended `exit 3` on the venv-less
  branch with the Persian intact.
- PowerShell 7 (`pwsh`) is **not installed on this host**, so the BOM'd file was
  never run under it. PS 7 honours a UTF-8 BOM by design, but that is reasoning,
  not a run. Recorded as unverified, not claimed.

**Attack 4 — could the owner-run receipt be a lie?** The log is append-only
across many runs, so the receipt quotes only the byte range this start produced
(offset 2290 → 3193, 903 bytes) and no earlier run's output is claimed as
evidence. The `1 start action` claim is checked against the report timestamp,
not by counting `action: "start"` lines across the directory, which would count
unrelated history. The receipt's `status.json` alias was confirmed byte-identical
in `ts` and `action` to the timestamped copy before either was cited.

**Attack 5 — is anything real being concealed?** The full suite has one failure
that is not mine and is not fixed silently:
`tests/test_alerts_web_banner.py::test_alerts_route_rechecks_canonical_buy_and_overlay`
asserts `"authorizeWebApi" in app/api/alerts/route.ts`, but HEAD's file uses
`authorizeDashboardEndpoint` (`git show HEAD:app/api/alerts/route.ts | grep -c
authorizeWebApi` → 0). Neither file is in M11.2's diff. It is flagged in
`CLAUDE_CONTINUATION_GUIDE.md` and left alone — fixing an unrelated TypeScript
test is out of scope, and a quiet cross-scope fix would be worse than the flag.
