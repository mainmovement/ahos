conflated.

| Spec claim | Committed state at HEAD `f6eb34f` | Evidence |
|---|---|---|
| `marker("gateway")` is a repo substring the spawned argv never carries | **still live.** `marker("gateway")` = `str(self.root / "node_modules")` | `launcher/orchestrator.py:126-127` |
| Gateway is spawned as `cmd /c npm run start` | **still live** | `launcher/components.py:233-245` (`_npm_cmd` → `gateway_command`) |

| `stop` must leave no listener on the gateway port | **delivered by reclamation, not by killing the recorded pid** | `launcher/orchestrator.py:646-658` |

So the mission is not "make idempotency work" — R7 already did that with the
pid-record fallback. The mission is: **make the marker true**, so the gateway
is identified the same way the engine and telegram are, the recorded pid *is*
the server, and the npm-wrapper/reparenting complexity stops being load-bearing
rather than merely compensated for.

## آرش (architecture) — approach (a), and why the fallback has to go

The spec offers two shapes and asks for one, documented. I take **(a)**: spawn
the gateway as

```
[<node>, <root>/node_modules/next/dist/bin/next, start|dev, --hostname, 127.0.0.1]
```

with `node` resolved from PATH, and keep `package.json`'s scripts as the human
entry point.

**Why (a) rather than (b).** Under (b) (`npm` + `descendant_of` + the
Toolhelp32 snapshot) the recorded pid remains the `cmd /c npm` wrapper, so every
identity question becomes a graph walk: is the listener a descendant of the
recorded pid, and has the wrapper died and reparented the listener to PID 1?
That is genuinely implemented already (`pk.process_snapshot`, `pk.descendant_of`,
`pk.fill_cmdlines`) and it works — but it is Windows-only machinery answering a
question that only exists because of the wrapper. Under (a) the recorded pid is
the server, its own argv carries the marker, and `pid_is_ours` answers
immediately on any OS. `stop()` kills the real listener instead of a stub whose
child outlives it. The reparenting failure mode stops being reachable.

**Existence checks, measured on this host, not assumed:**

- `where node` → `C:\Program Files\nodejs\node.exe`, `node v24.19.0`.
- `node_modules/next/dist/bin/next` exists (Next 16.2.6, `package.json`).
- `package.json`: `"start": "next start --hostname 127.0.0.1"`,
  `"dev": "next dev --hostname 127.0.0.1"` — so the argv (a) reproduces the
  scripts' flags exactly, including the loopback bind. No second server entry
  point is created.

**A marker the argv can actually carry.** Today the marker is
`<root>\node_modules`, which is a *directory*, not a substring of any command
line: `cmd /c npm run start --silent` contains no path at all. Deriving the
marker from the spawned argv like every other component does, the marker becomes
`<root>\node_modules\next\dist\bin\next` — the CLI path — which is present in the
argv of both `start` and `dev`. That is *tighter* than the old directory marker,
which is a strict improvement on the R3 finding (the old marker matched any
node process started from the checkout; the new one matches only a process
running this checkout's own next binary).

**The R7 fallback must be removed, not kept as belt-and-braces.** This is the
part that is easy to get wrong. `_pid_is_recorded_one` compares the recorded
`cmd` to the live command line after flattening quotes. Under (a) those two
strings disagree: we record `C:\Program Files\nodejs\node.exe
G:\robat\ahos\node_modules\next\dist\bin\next start --hostname 127.0.0.1`, and
`Get-CimInstance Win32_Process` reports the same process as
`"C:\Program Files\nodejs\node.exe" "G:\robat\...\next" start --hostname
127.0.0.1` — quoting and case differ. The flattening normalises quotes and case,
but the path separators/spacing as CIM returns them are not guaranteed to join
the way our argv does, and the moment the comparison fails, identity falls back
to `foreign_busy` and the exact R7 symptom returns *with* a correct marker
present. Keeping the strict-equality branch alongside a now-valid marker
reintroduces the disease it was written to cure. So the gateway special case is
deleted and `_pid_is_recorded_or_marked` becomes one line for every component.

**What stays as-is, and why.**

- `probe_gateway`'s 404 rule and `component_state`'s post-boot route-probe
  requirement: the marker proves we *spawned* the process, not that it is still
  serving our routes. Unchanged.
- `_reclaim_gateway_port`: a listener can still be stranded by a hard kill of
  the launcher (the console-close orphan case in `docs/ONE_CLICK.md`). It keeps
  working and its marker list updates automatically because it reads
  `sweep_markers()`.
- `child_env`'s `PORT` and `AHOS_GATEWAY_URL` injection: unchanged; `next start`
  honours `PORT` the same way `npm run start` did.
- `_npm_cmd("build")` and `db:restore-pglite`: these are one-shot foreground
  `subprocess.run` calls, not long-lived processes that need identity. They stay
  on npm, which is the honest use of npm here.

**One honest unknown.** `next start` under CTRL_BREAK: `terminate()` sends
CTRL_BREAK_EVENT to the process group first and escalates to `taskkill /T [/F]`.
Next.js installs graceful-shutdown handlers in recent versions, but I have not
verified which signals the Windows build acts on. The escalation path bounds the
damage either way, and the smoke's `stop` step measures the actual seconds. If
graceful shutdown does not fire, the receipt will show `force` instead of
`ctrl_break` — slower, not incorrect — and I will report it as measured rather
than claiming a graceful close.

**Authority surface:** `launcher/components.py`, `launcher/orchestrator.py`,
`tests/test_launcher_orchestrator.py`, `docs/ONE_CLICK.md`. No Lane A, no
`architecture/`, no gate, no policy, no freeze file. `launcher/processkit.py`
needs no change — its primitives (`pid_is_ours`, `process_cmdline`,
`spawn_detached`, `terminate`) are already marker-agnostic; only two docstrings
that narrate the npm shape get updated so they do not describe a mechanism that
no longer exists.

## پروانه (prompt / spec clarity)

The spec is unusually precise and I implement both named deliverables literally:

> "Unit: TestProcessMarkers-style test that the gateway marker is a substring of
> the argv actually spawned"

That lands in the existing `TestProcessMarkers` class, beside the engine and
telegram assertions it was written to complement. I add a second assertion to
the same test — **the argv must not be an npm wrapper** — because the class's
purpose is "the marker matches what we spawn", and under the old code the marker
*was* a substring of `str(self.root)` in a degenerate sense that let the failure
hide. Pinning the shape, not just the substring, is what makes the postmortem
non-recurrent.

> "box-reproducible `start; start; status; stop; status` … second start
> `gateway: HEALTHY already running (idempotent)` at the same pid … stop leaves
> no listener on the gateway port"

That is the `idempotent` smoke scenario, which already runs the full stack with
no default skips. It is the owner receipt.

One clarification I am recording rather than silently choosing. The spec's
acceptance says the second start must be "at the same pid". Under approach (a)
the pid-record reuse path is unchanged: `component_state` returns
`ours_running`, `_start_component` replays the recorded pid and does not spawn.
The marker change is what makes that branch reachable; the branch itself is not
touched. If the marker were still false, the branch was reachable only through
the R7 fallback, which the spec's own root-cause paragraph calls out as the
defect.

**package.json scripts are not edited.** The spec says keep them as the human
entry point, and `docs/CANONICAL_COMMAND_REFERENCE.md:174-176` documents
`npm run dev` / `npm run start` for operators. Those still work — they invoke
the same `next` CLI the launcher now invokes directly. No doc that an operator
reads needs to change.

## Implementation

(Sign-offs below are appended after each part is measured.)

### 1. `launcher/components.py` — argv the marker can be derived from

Added `node_executable()` (node on PATH — the same interpreter npm would hand
`next` to) and `next_cli(root)` (the script `npm run start` resolves to), and
`gateway_command` now returns the direct argv:

```python
def gateway_command(root: Path, mode: str = "prod") -> list[str]:
    """argv for the gateway in the given mode ..."""
    node = node_executable()
    if node is None:
        return []          # reported UNAVAILABLE by the caller, never npm'd around
    return [node, str(next_cli(root)), "start" if mode == "prod" else "dev",
            "--hostname", "127.0.0.1"]
```

`_npm_cmd` stays — `_npm_build` and `db:restore-pglite` still use it for
one-shot foreground scripts. `node_present` (preflight) is unchanged.

### 2. `launcher/orchestrator.py` — identity is the marker, for every component

- `marker("gateway")` derives from the command we spawn, like engine/telegram:
  `C.gateway_command(self.root, "prod")[1]` (the next CLI path), falling back to
  the old `node_modules` string only if the argv is unavailable.
- `_pid_is_recorded_one` **deleted**; `_pid_is_recorded_or_marked` is one line:
  `pk.pid_is_ours(info.get("pid"), self.marker(name))`. The R7 special case is
  gone because the marker is now true — see آرش.
- `_our_live_gateway_port` uses `pk.pid_is_ours(pid, self.marker("gateway"))`
  (still gated behind `pk.pid_alive`), so port adoption rides the same marker.
- `_start_process` reports `UNAVAILABLE` with a named reason when
  `gateway_command` returns `[]` (node or the next CLI missing) instead of
  silently falling back to npm, which would re-introduce the wrapper the mission
  exists to remove.
- Stale comments narrating `cmd /c npm run start` (`_our_live_gateway_port`,
  `_reclaim_gateway_port`, `stop`) are rewritten to the new shape.

### 3. `launcher/processkit.py`

Two docstrings only (`spawn_detached`, `port_owner`): they narrate the npm
reparenting as the reason `port_owner` exists. `port_owner`'s reason does not
disappear — a console-close orphan still strands a listener — but the wrapper is
no longer the cause, so the wording is corrected. No logic change.

### 4. `docs/ONE_CLICK.md`

New subsection under "Process identification on this host": the marker is
derived from the spawned argv for the gateway as well, why the npm wrapper was
removed, and what the new marker does *not* identify (route health — unchanged).
Finding R7 is annotated as superseded by the marker fix the way R6 superseded
R5, rather than deleted.

### 5. `tests/test_launcher_orchestrator.py`

- `TestProcessMarkers` gains the gateway marker-is-substring-of-argv assertion,
  for both `prod` and `dev`, plus an assertion that the argv is the direct node
  invocation and not an npm wrapper.
- The three gateway-adoption tests monkeypatch the identity primitives; where
  they patched `_pid_is_recorded_one`'s callees they now patch the marker path's
  callees, same assertions.

## Sign-offs

### رضا (red team) — attacks tried against the new identity path

1. **Does a tighter marker still kill something that is not ours?** The new
   marker (`<root>\node_modules\next\dist\bin\next`) matches *fewer* command
   lines than the old directory marker, never more: any string containing the
   CLI path also contains `<root>\node_modules`, so the match set is a subset.
   Measured against five representative command lines, the subset invariant
   holds in every case and the editor processes that R3 worried about
   (`node …\node_modules\.bin\tsc --noEmit`, `node …\vitest\vitest.mjs`) no
   longer match. Nothing widened.
2. **Can `stop` reach a dev server the *owner* started by hand?** Traced both
   kill paths. `_sweep_ours` is parentage-gated *first*
   (`launcher/orchestrator.py:736-744`): only a descendant of the launcher or a
   recorded component pid can become a candidate, and an owner's own terminal is
   neither — so the sweep cannot touch it. `_reclaim_gateway_port` does reach a
   process by TCP ownership, but only on a *gateway candidate port* and only
   after a marker match. An owner's `next dev` bound to 8300 could be hit —
   **this pre-dates M11.3** (the old directory marker matched it too) and M11.3
   narrows it. Recorded as an existing edge, not introduced here.
3. **Does the marker change break the reissued-pid guard?** The deleted
   `_pid_is_recorded_one` was the guard against Windows re-issuing a dead pid to
   an unrelated program. Its replacement is the marker: a re-issued pid's command
   line does not contain this checkout's next CLI path. Pinned by
   `test_reissued_gateway_pid_is_not_adopted` (`pid_is_ours → False` with
   `port_in_use → True` still yields `foreign_busy`) — assertion unchanged, only
   the patched callee moved with the code.
4. **Marker vs. live command line, on the real process.** Not a monkeypatch:
   `Get-CimInstance` returned
   `"C:\Program Files\nodejs\node.EXE" G:\robat\ahos\node_modules\next\dist\bin\next
   dev --hostname 127.0.0.1` and `pid_is_ours(pid, marker)` returned **True**.
   CIM quotes the interpreter and uppercases the extension, which is exactly the
   shape that would have made a kept-alongside `_pid_is_recorded_one` fail and
   re-open `foreign_busy` — confirming the decision to delete it rather than
   belt-and-brace it.
5. **`gateway_command` returns `[]`** (no node, no next CLI) → `_start_process`
   reports `UNAVAILABLE` with a named reason instead of falling back to the
   npm wrapper. Tried by monkeypatching `node_executable → None` and by a root
   with no `node_modules/next`; both yield `== []` and the test asserts it. The
   mission removes the wrapper, so the failure mode must be visible, not papered
   over.
6. **Graceful shutdown.** The receipt's two `stop` steps report
   `gateway: stopped (force, 1.0s)` / `(force, 0.9s)`. The gateway escalates to
   `taskkill /F` — but so do **engine** (`force, 0.9s`, `1.1s`) and **telegram**
   (`force, 0.9s`, `1.0s`), the pre-existing Python components whose argv did not
   change. Same flags, same escalation, so this is the host-wide behaviour for
   detached children, not a property of `next` or of this change. I also probed
   whether a CTRL_BREAK_EVENT reaches a windowless child in a new process group
   directly: inconclusive in this harness — no detached child fired its handler
   under either `CREATE_NO_WINDOW` or `CREATE_NEW_CONSOLE`, so the probe cannot
   isolate the cause and I report it as *not determined* rather than claiming
   `next` ignores the signal.
7. **Conflicting test root.** The first run of the new marker tests failed
   (`2 failed`) because `make_orchestrator(tmp_path)` roots at the *real repo*,
   not `tmp_path`, so a fake `node_modules/next` stood up under `tmp_path` was
   unrelated to the marker. Fixed by deriving the CLI from `orch.root` with a
   non-None guard, matching how the engine/telegram marker tests already depend
   on the real checkout. Recorded here because it is the one way this suite can
   silently lie about coverage.
8. **Stop a real orphan, in production, with no recorded pid at all.** Not a
   monkeypatch: an earlier attempt of this mission left an orphaned gateway on
   port 8300 (node pid 9184, parent 556 already dead, plus two engine daemons
   12756/14496 orphaned to the same dead parent). `Get-CimInstance` showed its
   command line containing this checkout's next CLI path, so the marker proved
   it ours *without* any pid record to consult — the exact no-record situation
   the old code could not handle. The sanctioned path
   `.venv/Scripts/python.exe -m launcher stop` stopped the paper engine and the
   gateway and reported `overall: STOPPED`; port 8300 was free afterwards, and
   PID 4708 and every other process I did not start were untouched. The owner's
   constraint "never kill a process that is not proven ours" held under a real
   orphan, not just a mocked one.

**Verdict: no weakening found.** The identity question is answered by a
substring of the process's own argv, on the process we actually spawned; every
kill path is still gated on proof of ownership; the change strictly narrows the
marker — and the marker alone was enough to identify and stop a real orphan with
no pid record.
