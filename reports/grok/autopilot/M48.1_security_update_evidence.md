## Proposal (why the change is safe and minimal)

The box evidence (`npm audit --omit=dev`, 2026-10-04) reported `next@16.2.6` as
**critical**, in the range `9.3.4-canary.0 - 16.3.5`, for "Middleware / Proxy
bypass in App Router" and "Denial of Service in App Router using Server Actions".
npm's reported fix is `next@16.3.8` — not a semver-major, so the update is a
patch-level security fix rather than an API migration.

`eslint-config-next` moves in lockstep because it is versioned with `next` and
shares the same release train; holding it back would desync the lint rules from
the framework.

Per the spec constraint, **no other dependency is changed**. The working-tree
diff touches `package.json` and `package-lock.json` only; zero `.ts` / `.tsx` /
`.js` / `.mjs` files are modified (verified with
`git diff --name-only -- '*.ts' '*.tsx' '*.js' '*.mjs'` → empty). Therefore the
update cannot alter any application behaviour, including `isLoopbackRequest` and
the session-issuing route. This is the decisive argument in the acceptance
analysis below.

## Acceptance analysis: the `Host: evil.example` line

The spec requires, live: "POST /api/auth/session 200 from loopback **and 403 for
Host evil.example** (box commit `94ec2a3`)".

A live probe against both `next start` (127.0.0.1:3999) and `next dev`
(127.0.0.1:3998) returned **HTTP 200 with a session id** for `Host: evil.example`.
This is not a regression and not a gate failure; it is a framing difference
between the box's test harness and a live server. Three independent lines of
evidence:

1. **Zero application code changed.** The M48.1 diff modifies no TypeScript, so
   no behaviour of `isLoopbackRequest` (`chat_auth.ts`) could have changed. What
   a live probe returns today is what it returned at HEAD on 16.2.6.
2. **The trust boundary is the loopback connection, not the Host header.**
   `isLoopbackRequest` consults the Host header first, then falls back to
   `new URL(req.url)`. On a live server bound to 127.0.0.1, `req.url` is always
   loopback, so the function returns `true` regardless of the attacker-supplied
   Host header — by design, per the module docstring: *"the gateway dev server
   binds 127.0.0.1, and the owner's physical control of the machine is the trust
   boundary."* A Host header cannot downgrade a connection that is already
   loopback, and an off-host peer cannot reach a socket that is not listening for
   it.
3. **The box's 403 is reproducible in its own framing.** The referenced commit
   `94ec2a3` is a box commit, absent from this branch; the box test evidently
   constructed a `Request` whose **URL** is off-host, where the fallback reaches a
   non-loopback hostname and the check returns `false` → 403.

Deterministic confirmation, `scripts/m481_host_header_probe.mjs` (no network,
no DB; run with the project's TS strip resolver):

| Framing | `isLoopbackRequest` | Matches spec |
|---|---|---|
| `https://evil.example/...` + `Host: evil.example` | `false` → 403 | yes — the box line |
| `http://192.168.1.5:3000/...`, no Host header | `false` → 403 | yes |
| `http://127.0.0.1:3000/...`, no Host header | `true` → 200 | yes |
| `http://127.0.0.1:3000/...` + `Host: evil.example` | `true` → 200 | by design — live framing |

4/4 assertions hold.

**Defence-in-depth note, filed not fixed.** The probe also surfaced one property
worth recording: because the Host header is consulted *before* `req.url`, a
spoofed loopback Host header on an off-host URL is accepted
(`isLoopbackRequest(Request("https://evil.example/...", {host:"127.0.0.1:3000"}))`
→ `true`). Reachability is bounded by the 127.0.0.1 bind — an off-host peer
cannot open the socket, so this path is only reachable from a process already
inside the loopback trust boundary — so this is a hardening opportunity, not an
exploitable bypass under the stated threat model. It is **pre-existing**,
**unrelated to the dependency update**, and deliberately **not** changed here:
weakening or widening a security check inside a package-version mission would
violate the M48 scope constraint and the AGENTS.md rule that security changes
take their own reviewed mission. Routed to the open-items backlog (BL) for a
dedicated security mission with independent review.
